## STALL REPORT (the binding part)

Ordered by implementation sequence. PRD citations refer to the inlined fullprompt.md supplied with this task; repository citations refer to this checkout. Recommended sentences are proposed amendments, not claims that the PRD already specifies them.

1. **PHASE / MODULE: t1 schema / observation scope.**
   - **DECISION I CANNOT MAKE:** The implementation explicitly adds retraction, but Out of Scope says “A tombstone / retraction mechanism. See Gotcha 6. No `retracted_at`, no `replaced_by`. If it is needed it is a schema change, and nobody has decided to need it.” Q1 also says “`entity_alias` has no retraction (Gotcha 6)”. These contradict Q2a and Implementation Decisions 1–4.
   - **WHY IT STALLS ME:** Obeying the exclusion removes the seventh column and the second writer; obeying Q2a implements functionality explicitly excluded elsewhere. This changes persisted schema and every reader.
   - **RECOMMENDED RESOLUTION:** Replace the exclusion with: “Observation-based withdrawal and reinstatement are IN scope; mutable `retracted_at` and successor-link `replaced_by` columns are out of scope. Q2a and Implementation Decisions 1–4 supersede all older statements that aliases have no retraction.” Remove the stale Q1 rationale.

2. **PHASE / MODULE: t2 observation writers, then t3/t4 ordering.**
   - **DECISION I CANNOT MAKE:** “Readers take the LATEST observation … by `observed_at`” supplies no winner for equal timestamps. “`observed_at` and `ingest_batch_id` are filled by the writer exactly as the other write paths fill them” does not actually name a capability-writer clock policy: `register()` passes prepared mappings directly to load (`src/kbutillib/domains/kbase/berdl/clearinghouse_capability.py:1709`), and registry projection retains caller-provided values (`:1817`, `:1968`). The sharder instead has a concrete run-time policy (`src/kbutillib/domains/kbase/berdl/clearinghouse_shard.py:4980`).
   - **WHY IT STALLS ME:** Equal-time present/withdrawn events are possible with timestamp precision limits and concurrency. SQL row order can reinstate or withdraw the same alias arbitrarily. Generating a batch identifier without an agreed tie rule does not solve this. Choosing producer event time versus call time also changes which assertion wins.
   - **RECOMMENDED RESOLUTION:** Add: “The capability writers generate a non-null UTC observation timestamp and fresh ULID ingest_batch_id per call; caller metadata overrides are refused. Every latest-event reduction orders by observed_at DESC, ingest_batch_id DESC, then observation DESC (withdrawn wins an exact provenance tie). This defines deterministic tie behavior, not global causal ordering across writers.” If source event timestamps are required instead, specify that input explicitly before implementation.

3. **PHASE / MODULE: t3 `aliases()` history contract.**
   - **DECISION I CANNOT MAKE:** “`aliases()` returns the OBSERVATION HISTORY” and is the answer to “what happened to this accession”, but it also returns “one dict per distinct five-tuple” with “`MAX(observed_at)`”. Test 10a requires all three persisted `present -> withdrawn -> present` rows; the five-tuple read reduction necessarily merges the first and third.
   - **WHY IT STALLS ME:** After that sequence, the advertised history returns only withdrawn at t2 and present at t3. It cannot show the original registration or distinguish repeated assertions from retries. I must choose between the explicit five-tuple projection and event-history semantics; both cannot be delivered.
   - **RECOMMENDED RESOLUTION:** To retain the specified projection, add: “aliases() returns the most recent occurrence of each observation state per four-tuple, NOT full event history; repeated same-state events are intentionally collapsed. Test 10a checks raw persisted rows, and no public complete event-history accessor is promised.” If actual history is required, replace five-tuple deduplication with exact seven-column duplicate removal and add a history test for all three transitions.

4. **PHASE / MODULE: t3 `aliases(current_only=True)`.**
   - **DECISION I CANNOT MAKE:** The body calls this “just the live set”, but test 13a says that after a present followed by withdrawn, “`current_only=True` returns only the reduced latest.” That reduced latest is a withdrawn row, not a live alias.
   - **WHY IT STALLS ME:** Returning an empty list and returning a withdrawn dict are different public behaviors. A caller using the advertised live set can act on an explicitly withdrawn identifier if I implement the test literally.
   - **RECOMMENDED RESOLUTION:** Add: “current_only=True first reduces each four-tuple to its latest observation and then excludes withdrawn winners; test 13a expects an empty result for a finally withdrawn four-tuple.” If a latest-state inspector is intended instead, explicitly say it includes withdrawn rows and stop calling it the live set.

5. **PHASE / MODULE: t3 reverse lookup / collision detection.**
   - **DECISION I CANNOT MAKE:** “It resolves against the LATEST observation for the pair: if that observation is withdrawn … returns None” conflicts with the earlier reduction per `(entity_type, entity_hash, alias_source, alias_id)` and “On more than one distinct entity_hash … it RAISES.” Neither clause says whether collision detection sees all historical hashes or only current present mappings.
   - **WHY IT STALLS ME:** Consider hA present at t1, hB present at t2, hA withdrawn at t3 for the same source/id. A pair-global winner returns None; per-four-tuple current-state resolution returns hB; counting historical hashes raises. All three can be defended from the wording. The first loses a valid mapping; the third makes a corrected collision permanently unresolvable.
   - **RECOMMENDED RESOLUTION:** Add: “resolve reduces independently per (entity_type, entity_hash, alias_source, alias_id), discards withdrawn winners, then counts distinct entity_hash values across surviving rows: zero returns None, one returns that hash, more than one raises AliasAmbiguousError. Historical withdrawn mappings do not cause ambiguity.” Add the hA/hB sequence above as a regression test.

6. **PHASE / MODULE: t3 hash-filter transport.**
   - **DECISION I CANNOT MAKE:** The PRD mandates entity_hash is “parameter-bound, never inlined, exactly as every other hash lookup”, while permitting `engine=None`/explicit engines and default Trino. The repository's actual shared seam explicitly inlines validated hash parameters off-pod and on Spark (`src/kbutillib/domains/kbase/berdl/clearinghouse_capability.py:427`, `:458`). The available off-pod transport has no bind channel.
   - **WHY IT STALLS ME:** Reusing `_run` violates the literal never-inline rule. Refusing Spark/off-pod hash filters removes capabilities available on the neighboring readers and makes engine selection behave differently. Implementing a new remote bind protocol is outside this change and unsupported by the given transport.
   - **RECOMMENDED RESOLUTION:** Replace the rule with: “Build hash predicates with placeholders and canonicalized params, and execute through the existing _run binding regimes: true binding on in-pod Trino and validated hex inlining on Spark/off-pod. Do not interpolate hashes in the alias SQL builder itself.”

7. **PHASE / MODULE: t5 CLI resolve errors.**
   - **DECISION I CANNOT MAKE:** Implementation Decision 3 says “do not reuse ValueError” for contested mappings and requires AliasAmbiguousError, but Decision 5 says the CLI “exits non-zero only on the collision ValueError.” Unknown alias_source must separately raise ValueError. There is also no stated JSON failure envelope/exit behavior for that invalid user input.
   - **WHY IT STALLS ME:** Catching ValueError misses a distinct collision exception unless I quietly choose inheritance that contradicts the stated distinction. Following “only” literally makes an invalid source a successful CLI answer, indistinguishable by exit status from not found. Letting exceptions escape can bypass the required one-envelope contract.
   - **RECOMMENDED RESOLUTION:** Add: “AliasAmbiguousError is a distinct exception, not a ValueError subclass. resolve CLI emits one failure envelope and exits 1 for AliasAmbiguousError or invalid alias-source input; transport/query errors also exit non-zero. A valid lookup with no current mapping emits a successful envelope and exits 0.” Replace “collision ValueError” with “AliasAmbiguousError”.

8. **PHASE / MODULE: t7 runbook / archive-member join guidance.**
   - **DECISION I CANNOT MAKE:** Documentation must state that “the archive-member form needs its #<entry> fragment split off as well as the scheme stripped”; Gotcha 12 presents this as the extra step needed to join fasta_reference to `kbdl_fasta_object.alias_id`. But the vocabulary defines that alias as the member's rule-B FASTA content hash, while the archive pointer is `obj://<archive_id>#<entry>`.
   - **WHY IT STALLS ME:** Stripping produces the ARCHIVE id, not the member FASTA content hash. The existing preset explicitly describes a pointer INTO the archive (`src/kbutillib/domains/kbase/berdl/backfills/kbdl-genome-archives.toml:75`, `:111`), and the adapter emits archive_object_id and entry_name separately (`src/kbutillib/domains/kbase/berdl/clearinghouse_shard.py:4480`). It does not emit a fasta_object_id in that record. I cannot write the prescribed join guidance as a correct operational procedure. An archive contains multiple genomes; treating its id as a per-genome identifier causes empty joins or many-entity collisions.
   - **RECOMMENDED RESOLUTION:** Replace that guidance with: “For standalone obj://<fasta_object_id> references, removing the scheme recovers kbdl_fasta_object.alias_id. For obj://<archive_id>#<entry>, parsing recovers an archive/member locator, NOT the member's FASTA hash; join through entity_hash or an explicit archive/member-to-member-hash mapping. Never label archive_id as kbdl_fasta_object for a member.” The mapping/adapter work remains a separately scoped follow-on.

## FREE CRITIQUE (non-binding)

**Recommendation: do not hand this PRD to an unattended implementation agent until the observation reduction and precedence contracts above are patched.** The schema additions themselves are straightforward. The new observation model has not been reconciled throughout the document, and calling the read verbs “shallow” hides decisions that determine which genome a consumer acts on.

- **The manifest phase is an end-to-end sharding and ingest change, not merely a fourth grammar kind.** Implementation Decision 6 requires emitted alias rows, so I would treat the following modifications as implied implementation work, not ask the author to choose a mechanism. The Sources Consulted claim that ingest helpers are “uninformative” because “a future alias-via-shards path would need them” is false for the path this very PRD requires. Relevant seams:
  - `src/kbutillib/domains/kbase/berdl/clearinghouse_manifest.py:306`: Source currently carries only content/result mappings; alias entries must survive parsing.
  - `src/kbutillib/domains/kbase/berdl/clearinghouse_manifest.py:965`: every plan currently uses table_name(etype, kind), which must continue refusing alias per t1. Alias needs an explicit generic-table branch.
  - `src/kbutillib/domains/kbase/berdl/clearinghouse_backfill.py:232`: _target_tables also constructs every target with table_name; changing only the planner leaves backfill planning broken.
  - `src/kbutillib/domains/kbase/berdl/clearinghouse_shard.py:5013`: _build_row currently produces one dict per record, and stamps entity_type only for entity/result. Alias fan-out must produce all declared entries and stamp present plus entity_type, with null omission per entry rather than dropping other aliases for that entity.
  - `src/kbutillib/domains/kbase/berdl/clearinghouse_shard.py:5360`: _key_spec uses entity_hash-only dedup for non-result/non-registry kinds. Inheriting it would discard all but one alias for an entity. Use the alias five-tuple, and ensure generic-table batches can contain multiple entity types without collapsing them.
  - `src/kbutillib/domains/kbase/berdl/clearinghouse_shard.py:5722`: output columns still go through schema.column_names(entity_type, kind), which cannot name alias. Use the new accessor here and audit equivalent schema consumers.
  - `src/kbutillib/domains/kbase/berdl/clearinghouse_ingest.py:226`: key_columns_for_table explicitly rejects entity_alias; add its five-tuple. Range slicing can still use entity_hash. The capability's existing-key read calls this helper (`src/kbutillib/domains/kbase/berdl/clearinghouse_capability.py:2852`). Preserve the legal-orphan/no-referential-check posture.
  - Add one real-path test: a tiny file manifest emits two aliases for one hash, one null alias entry, and another entity type into entity_alias; shard to parquet, verify all surviving identities, then exercise fill-only ingest against a stub. The enumerated plan/null tests alone do not prove that a declared alias ever reaches a load.

- **Programmatic bulk loads can resurrect never-before-seen wrong mappings after a withdrawal.** Five-tuple fill-only suppresses a present row only if a present event already exists. If observe_alias first records withdrawn for a four-tuple that never had present, a later bulk register_aliases call adds a newer present and resolves it again. This follows the stated rules and is not an implementation ambiguity. Decide whether that is acceptable; test it. Likewise an old bulk observation retried after an earlier present remains suppressed after withdrawal, whereas the same content first loaded late can reinstate: arrival history affects outcomes.

- **observe_alias retries are not idempotent.** A network timeout after commit followed by retry appends another assertion with a later timestamp. Interleaving an opposite observation can change final state. The PRD explicitly chooses always-append; document that operational consequence rather than describing every retry as free. A future caller-supplied event id would separate idempotent event delivery from bulk fill-only.

- **The legal-orphan rationale is temporally misleading.** “Before it has hashed the contigs” cannot literally describe a valid alias write: validate_alias requires the final canonical 64-hex entity_hash. The supported ordering is before the entity ROW is loaded, provided its hash is already computed or supplied by a trusted source. The no-referential-check decision is implementable; its producer example needs this correction.

- **The proposed integrity report does not detect contested aliases.** Gotcha 9 says the orphan/integrity report “should be watched” for duplicate-mapping producers. Two present mappings to two existing entities are not orphans, so orphan_total can be zero while resolve fails. A separate active collision count is useful; do not imply orphan monitoring catches this.

- **Existence-only preflight does not prevent schema drift.** Gotcha 3 correctly notes bootstrap does not verify columns, then suggests existence checking addresses the same hazard. It does not. At minimum OP-C5 must verify all seven exact names/types and partitioning. A future alias-specific schema assertion would provide defense against later manual drift without changing _assert_lake5_schema.

- **Health deployment order is material.** _build_health currently unconditionally calls its integrity accessor (`src/kbutillib/interfaces/cli/clearinghouse.py:1058`). Adding an unconditional alias query means deploying code before OP-C5 can break health on an otherwise valid old namespace. The PRD explicitly stages table creation after merges; specify operationally that health runs only after creation, or define a deliberate missing-table response. A query failure is distinct from a legitimate non-zero orphan finding and should not be silently reported as zero.

- **The health dict and writer report deserve concrete examples.** orphan_total and orphans_by_source are named, but the grouped row/list-versus-mapping representation and the reduced population key are not. The registry writer uses lists of hashes for written/already_present (`src/kbutillib/domains/kbase/berdl/clearinghouse_capability.py:1940`); alias reports need unambiguous five-tuple identities if following that shape. These are routine API representation choices an implementer can make, not stop-the-build ambiguities in this review. Add examples before downstream clients depend on them.

- **The missing external scan is not itself a build blocker.** Q1/Q2/Q5/Q7/Q11 have explicit decisions. I did not reopen those settled design choices or independently verify biological statistics. ncbi_taxon in particular is inherently many-genomes-to-one-id; resolve raising for that source is a deliberate consequence of Q7, not evidence the implementation should silently choose a genome.

No live table counts, Iceberg partition metadata, production schemas, or upstream identifier claims were verified here. The report does not claim this feature can be marked finished from this worktree.
