## FINDINGS

**Recommendation: preserve the chosen thin table, but make its historical-observation semantics and reverse-lookup ambiguity explicit in the PRD.** Prior art supports generic crosswalks; it does not support treating every external reference as an eternal, uniquely invertible content identity. The most material conflicts are properties 3 (no withdrawal interpretation), 5 (discarded mapping method), and 6 (assumed unique reverse lookup). Evidence and qualifications follow below. This is an external scan, not a proposal to silently change the seven selected design properties.

Sources accessed October 25, 2026. Versions are named when the source specifies one; unversioned “latest” and repository branch links can change. Recommendations and deductions are explicitly marked as inference; no production source tree was researched or modified.

| Specific question / property | Answer from surveyed prior art | Consequence for this PRD (inference) |
| --- | --- | --- |
| 1. Closed vs open; property 2 | Identifiers.org curates namespaces; Bioregistry reviews prefix changes outside consumers. Neither publishes a numeric scaling threshold. Reltio also registers sources. | A ten-value tuple is defensible. Preserve source spellings so a registry can later govern the same keys without rewriting rows. |
| 2. Missing confidence; property 5 | Ensembl distinguishes mapping methods and stores alignment evidence; SSSOM separates predicate, justification, actors and optional confidence. | A floating confidence is not mandatory for strict aliases, but omitted method/actor evidence prevents method-specific filtering and audits unless retained elsewhere. |
| 3. Obsolescence; property 3 | NCBI uses status/history; GO uses obsolete/replacement distinctions; Reltio uses deletion dates. | Positive-only union answers “ever observed,” not “currently valid.” Disappearance alone also cannot prove an assertion wrong. |
| 4. Many-to-many; property 6 | Ensembl explicitly permits it; UniProt documents the P29358 split; InterMine handles ambiguity separately from uniqueness. | Count distinct targets before returning a scalar. Specify ambiguity behavior; do not silently choose a row. |
| 5. Partitioning; property 7 | Iceberg documents partition-boundary/file-size limits; Delta warns about small partitions/batches. No vocabulary-crosswalk benchmark found. | Keep source partitioning as a workload assumption, with file-size/skew measurement and compaction cost acknowledged. |
| 6. Reuse | CURIE tools handle lexical namespaces, not biological identity or Iceberg persistence. | No surveyed tool replaces the table. Optional prefix helpers belong at ingestion/export boundaries. |

Property 1 has strong analogues in Ensembl's polymorphic object links, UniProt's generic ID-type column and InterMine's BioEntity cross-references. Property 4 (legal orphans) was **not** validated by an equivalent surveyed implementation: relational links and mapping-service failures are not evidence for orphan hash rows. An inverse health report can describe missing targets but cannot establish that a source identifier uniquely determines future content (inference).

A further concrete concern in the supplied vocabulary is `ncbi_taxon`: a taxonomy identifier names a taxon, rather than a particular genome assembly. [NCBI assembly summary documentation](https://ftp.ncbi.nlm.nih.gov/genomes/README_assembly_summary.txt), columns 1, 6 and 7, distinguishes versioned assembly identifiers from organism/species taxonomy IDs. Treating this as a genome alias makes the inverse a membership query, which can legitimately return several genomes. No corpus cardinality was measured here. Likewise, provenance record ids and workspace refs require their own version/scope contracts before scalar inversion can be asserted; this scan did not inspect those internal definitions.

## PRIOR ART SURVEYED

### Ensembl: generic links carry method and evidence
[Core schema v116](https://asia.ensembl.org/info/docs/api/core/core_schema.html): `xref` contains `external_db_id`, `dbprimary_acc`, `version`, `info_type`, `info_text`; `external_db` holds `db_name`/`db_release`. `object_xref` links via `ensembl_object_type`, `ensembl_id`, `xref_id`, `analysis_id`. It explicitly permits an xref to link multiple Ensembl objects. This supports property 1 but contradicts property 6's scalar inverse. `identity_xref` separately records percentage identities, alignment coordinates, score and e-value. `info_type` distinguishes DIRECT, DEPENDENT, SEQUENCE_MATCH, PROJECTION, COORDINATE_OVERLAP and CHECKSUM; these are mapping methods, not a calibrated confidence probability. This contradicts property 5 if equivalent distinctions matter.

[REST example](https://rest.ensembl.org/documentation/info/xref_name) exposes HGNC BRCA2 as DIRECT with `info_text` naming `ensembl_manual`, alongside DEPENDENT UniProt gene-name links. [Another example](https://rest.ensembl.org/documentation/info/xref_id) exposes a UCSC link as COORDINATE_OVERLAP. Without equivalent metadata, users cannot filter direct versus projected/overlap assertions, select manually generated links, or audit alignment-quality thresholds. A batch id can support those operations only if it joins to preserved, sufficiently granular evidence elsewhere (design inference). I have not established when these fields were introduced or any retrospective migration cost.

### Registry prior art: controlled and extensible, not arbitrary strings
[Identifiers.org resolution](https://docs.identifiers.org/pages/resolving_mechanisms.html) separates namespace prefix, local accession, and optional provider code (`pdbe/pdb:2gc4`). Multiple providers are locations for a namespace, not different biological identities. [Registry FAQ](https://docs.identifiers.org/pages/faq.html) documents identifier regex, namespace, locations, examples, timestamps and deprecation status; curator confirmation governs updates. Thus property 2 differs in governance location, not in whether vocabulary is controlled. Its MIRIAM URNs were superseded by HTTP URIs in 2011 while keeping namespaces and interconversion. [Platform migration](https://docs.identifiers.org/pages/migration.html) retained existing identifier resolution despite API changes: a concrete compatibility pattern.

[Bioregistry data model](https://biopragmatics.github.io/bioregistry/datamodel/) has canonical/preferred prefixes, prefix synonyms and resource deprecation flags. [Governance](https://github.com/biopragmatics/bioregistry/blob/main/docs/GOVERNANCE.md) requires issues/PRs, tests and review for additions, merges and splits. [Downloads](https://bioregistry.io/download) expose registry snapshots separately from consumers. It is a complementary metaregistry/resolver, not evidence that Identifiers.org ceased operating ([project description](https://www.bioregistry.io/)).

**Question 1:** None of these sources supplies a row-count or organization-count threshold, nor establishes that either project began as a closed application tuple. The proposed premise cannot be treated as measured history. Inference: the pressure is independently governed producers and prefix metadata/change cadence, not number of alias rows. Ten internally governed sources can reasonably remain a tuple. A future registry can initially use the existing `alias_source` strings as stable keys, attach synonyms/metadata externally, and change validation to a versioned registry allowlist without rewriting historical rows. Renaming stored keys is unnecessary if readers normalize synonyms; splitting a previously ambiguous namespace may require additional evidence and cannot be solved by a prefix synonym alone.

### NCBI: cross-references are typed relations, with explicit history
The [Gene FTP README](https://ftp.ncbi.nlm.nih.gov/gene/README) was fetched directly with Python HTTPS after the browser tool could not open it. `gene2accession` is recalculated daily: `tax_id`, `GeneID`, `status`, RNA/protein/genomic `accession.version` fields, positions, orientation and assembly. Rows are genomic/RNA/protein sets, not equivalence assertions. A chromosome accession appearing against multiple genes is an immediate example of a cross-reference that must NOT become a gene identity alias. Status includes SUPPRESSED; the file can deliberately retain obsolete RefSeq accessions until the next genomic annotation. Presence alone is not proof of currency.

`gene2ensembl` carries `tax_id`, `GeneID`, `Ensembl_gene_identifier`, RNA accession/version and Ensembl RNA id, protein accession/version and Ensembl protein id. Matches depend on feature overlap/splice criteria, and only best matches are reported; the README warns that its Ensembl links can disagree with `gene_info` dbXrefs because processing differs. `README_ensembl` separately records NCBI/Ensembl releases, assemblies and comparison date. This is evidence that a thin mapping file can work with method/release context external to rows, not evidence that matching is context-free fact (property 5).

`gene_history` has current `GeneID`, `Discontinued GeneID`, `Discontinued Symbol`, `Discontinue Date`, and `tax_id`. [Assembly summary documentation](https://ftp.ncbi.nlm.nih.gov/genomes/README_assembly_summary.txt), also fetched directly, separates current and historical files and defines `version_status` as latest/replaced/suppressed. `assembly_accession` includes version; `gbrs_paired_asm` and `paired_asm_comp` distinguish paired GenBank/RefSeq assemblies and whether they are identical/different. Neither a paired accession nor an unversioned accession is automatically a content-digest equivalence.

These lifecycle fields and history files contradict property 3 **if** the proposed union is meant to answer current identity: retaining all positive observations cannot express withdrawal. They support retaining historical observations with a separate interpretation layer. No NCBI-to-Iceberg throughput benchmark or historical field-addition cost was established.

### UniProt: the closest thin-table precedent still has lifecycle semantics
The [2011 service paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC3072559/) explicitly documents `idmapping.dat` as three tab-delimited columns: UniProtKB accession, ID type, ID. This closely supports the proposed generic thin mapping shape; it is not evidence for orphan admission, append-only accumulation, or inverse uniqueness. The original FTP README timed out, so the primary publication is the verified source for the file shape.

The [2025 UniProt API paper](https://doi.org/10.1093/nar/gkaf394) describes asynchronous `/idmapping/run`, `/idmapping/status/{jobId}`, `/idmapping/results/{jobId}`, and `/idmapping/stream/{jobId}`; jobs accept up to 100,000 IDs and results expire after seven days. This is a biological mapping provider, not a replacement for an internal Iceberg alias store.

[UniProt accession documentation, modified June 12, 2026](https://www.uniprot.org/help/accession_numbers) provides a decisive one-to-many example: P29358 was demerged into P68250 and P68251; original identifiers remain secondary accessions on split entries. Deleted accession lists are maintained separately. [Entry history](https://www.uniprot.org/help/entry_history) separates entry and sequence versions and provides archived records. Therefore an accession is an evolving record identifier, not inherently an immutable sequence digest. This contradicts property 6 for secondary IDs and for unversioned records accumulated across content changes. The exact two successor sequences were not downloaded or hashed here; this is verified identifier multiplicity, not a measured count of distinct clearinghouse hashes.

### GO/OBO: identity aliases, retirement and replacement are different relations
[GO ontology documentation](https://www.geneontology.org/docs/ontology-documentation/) describes alternate IDs as preserved IDs after terms of identical meaning merge. Obsolete terms retain IDs, are marked obsolete, and lose relationships; comments explain the change. GO dbxrefs may describe identical **or similar** objects, so converting every dbxref to strict identity would overstate the source.

[OBO format guide 1.4](https://owlcollab.github.io/oboformat/doc/GO.format.obo-1_4.html) distinguishes `alt_id`, `is_obsolete`, `replaced_by`, and `consider`. Replacement permits automatic reassignment; `consider` requires expert inspection. Both can have multiple targets. Thus aliases, safe replacement and suggested replacement cannot be collapsed into one unqualified edge. Properties 3 and 5 cannot reproduce this lifecycle/decision surface. A retirement record need not delete old observations, but some status/event or release-selection mechanism is required for a current-state answer (inference).

### GA4GH refget: digest identity requires a specified equivalence relation
[Refget overview](https://ga4gh.github.io/refget/) distinguishes Sequences v2 (approved 2024) and Sequence Collections v1 (approved 2025). [Sequences specification](https://ga4gh.github.io/refget/sequences/) defines sequence normalization/checksums and deprecates the older TRUNC512 form. These are identifiers derived from content, unlike a provider's accession for an evolving record.

[Sequence Collections v1.0.0](https://ga4gh.github.io/refget/seqcols/) uses collated `names`, `sequences`, and `lengths`, with a schema declaring which attributes are inherent to the digest. Its digest algorithm is SHA-512 truncated to 24 bytes and base64url encoded, not the proposed 64-character SHA-256. [Coordinate-system attributes](https://github.com/ga4gh/refget/blob/master/docs/seqcols/README.md) can match collections having the same names/lengths but different sequences. Therefore compatibility, record cross-reference and content identity are distinct operations. Inference: foreign assembly MD5 values should be namespaced by their actual canonicalization contract; a hash-looking string alone does not establish equivalence with the internal content hash. This source supports treating digest namespaces explicitly but cannot validate either KBase or BV-BRC's hashing contract, which was outside this scan.

### Lakehouse partitioning: documented mechanics, no crosswalk-specific benchmark
[Iceberg Spark writes](https://iceberg.apache.org/docs/latest/spark-writes/) says files cannot cross partition boundaries or exceed their writing task's data. Hash distribution by partition values became the Spark writer default in Iceberg 1.2.0; AQE can split/coalesce tasks. [Configuration](https://github.com/apache/iceberg/blob/main/docs/docs/configuration.md) gives a 512 MiB target file size, not a minimum guaranteed size. [Delta best practices](https://github.com/delta-io/delta/blob/master/docs/src/content/docs/best-practices.mdx) suggests at least 1 GB per partition and warns that small continuous batches accumulate files. That is Delta guidance, not a measured Iceberg threshold.

**Question 5:** No measured source-vocabulary crosswalk benchmark was found. Inference from those mechanics: ten source values avoid huge partition cardinality, but rare sources still get tiny files; a dominant source can remain large. Source partitioning helps `resolve(source,id)` prune other sources, but an entity lookup without source filters visits all partitions. Adding time partitions would multiply small partitions and poorly match these lookups. Benchmark source-only against unpartitioned/sorted files and, only at sufficient scale, bounded `bucket(N, entity_hash)` for entity lookups or alias-id clustering for reverse lookups. There is no universal better key for both directions. [AWS Iceberg guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/apache-iceberg-on-aws/best-practices-read.html) documents bucket transforms, write distribution and regular compaction. Measure per-source bytes/batch, file counts and sizes, files scanned, latency, skew and compaction cost before claiming property 7 is optimal.

### BioMart and InterMine: multiplicity is visible to readers
The [Ensembl BioMart walkthrough](https://training.ensembl.org/text_module/human_biomart_walkthrough) selects gene/transcript stable IDs plus external NCBI and GO identifiers; it explicitly explains multiple output rows per gene through multiple transcripts and GO terms. This is a query projection over relationships, not a proof those identifiers are equivalent. DISTINCT removes duplicate projected rows, not distinct biological targets (inference).

[InterMine Python model documentation](https://intermine.org/intermine-ws-python/intermine.html) shows `Gene.crossReferences` as a collection whose reverse reference is `subject`. [Web configuration documentation](https://intermine.readthedocs.io/en/latest/webapp/properties/web-properties/) describes CrossReference identifier and data source. [ID resolver documentation](https://intermine.readthedocs.io/en/latest/database/data-sources/id-resolvers/) requires organism context and documents zero matches → NULL, one → identifier, multiple → NULL; callers can count resolutions. It even warns that changed MGI input formatting invalidates an old prefix configuration. This is concrete precedent for retaining a scalar return only with an explicit ambiguous-case policy, rather than assuming uniqueness. These are older documentation examples (2018-era, site points to newer 5.0.0 docs); no current InterMine database instance was queried.

A direct schema check located [`bio/model/core.xml:35`](https://github.com/intermine/intermine/blob/cac4eb42c069d70a390247285b34f93516167595/bio/model/core.xml#L35): `CrossReference.identifier` is a String, `source` references `DataSource`, and `subject` references `BioEntity`. [`DataSource` at line 41](https://github.com/intermine/intermine/blob/cac4eb42c069d70a390247285b34f93516167595/bio/model/core.xml#L41) carries name, URL, description, publications and datasets. This confirms a generic linked model with externalized source metadata. This schema excerpt alone does not prove uniqueness or physical foreign-key enforcement.

### Master-data crosswalks and semantic mapping standards
[Reltio Crosswalks](https://docs.reltio.com/en/objectives/model-data/data-modeling-at-a-glance/data-modeling-operation/define-crosswalks-for-data-sources/crosswalks) requires registered sources and identifies crosswalks through `type`, `value`, optional `sourceTable` and URL. Shared crosswalks imply merging entities; `dataProvider` distinguishes attribute-supplying sources from external links. This supports closed/registered vocabulary and functional inverse semantics **when actively enforced**; it does not justify assuming the same invariant in a non-enforcing lakehouse. [Indexed fields](https://docs.reltio.com/en/developer-resources/system-administration-apis/system-administration-apis-at-a-glance/search-api/fields-indexed-in-elastic-search/entity-fields-indexed-for-elastic-search/crosswalks-fields-indexed) include `createDate`, `updateDate`, `deleteDate`, `reltioLoadDate`; `deleteDate` records source removal. That directly contrasts with property 3's lack of withdrawal state.

[SSSOM development specification](https://mapping-commons.github.io/sssom/dev/) represents mappings as explicit subject/predicate/object assertions with mapping justification, author/reviewer metadata and optional confidence. It addresses a broader semantic mapping problem than strict identity aliases. [Release history](https://github.com/mapping-commons/sssom/releases) records addition of `mapping_set_confidence` in PR #446: evidence that confidence-related metadata can be added later. This is set-level confidence, not evidence that Ensembl retrofitted per-link confidence, and the release notes provide no measured migration cost. Inference: adding nullable columns is easy relative to reconstructing historical methods, actors or confidence that ingestion discarded.

### What a thin append-only observation table can and cannot recover

**Question 3, precise limitation (inference from the lifecycle examples above):** if a true assertion and a subsequently withdrawn assertion both leave exactly the same six-column positive row set, no reader query over those rows can distinguish the histories. `observed_at` dates the observation; it does not encode withdrawal. `SELECT DISTINCT` removes repeated observations but cannot repair a wrong edge. An entity still existing also does not mean every identifier link to it remains valid; the inverse health report in property 4 therefore addresses a different issue.

An append-only **event** log with assert/retract operations, or a retained history plus authoritative release/current-state selection, can preserve history while expressing withdrawal. That is an architectural escape route, not a claim that the currently specified row shape already supports it. Batch selection works only if batches are complete, scoped snapshots with recorded completeness; absence from an incremental batch is not a tombstone. A future nullable evidence column can describe new rows, but old evidence needs source replay/backfill and may be unrecoverable. [Iceberg evolution documentation](https://iceberg.apache.org/docs/latest/evolution/) supports metadata-only schema additions and partition-spec evolution without rewriting existing files; it does not manufacture missing historical semantics. Older data remains under older partition specs, so changing partitioning does not immediately recluster it.

**Question 4, scalar policy (inference):** distinguish zero, one and multiple distinct target identities. Count `(entity_type, entity_hash)` pairs when the API omits entity type; returning only a hash also hides cross-type ambiguity. Define whether multiple targets raise an ambiguity error or return None as InterMine's documented resolver does. A health report can enumerate collisions without refusing ingest, consistent with properties 3/4. It cannot make the functional dependency true. If strict scalar semantics are retained, each vocabulary's contract must exclude membership relations (taxon→genomes), unversioned changing records and ambiguous secondary identifiers, or explicitly accept unresolved cases.

**Question 2, concrete lost operations:** Ensembl's fields permit selecting DIRECT rather than PROJECTION/COORDINATE_OVERLAP links, filtering `identity_xref` by score/percentage identity, and tracing `analysis_id` or manual-generator text. SSSOM permits selecting assertions by justification/author/reviewer. The proposed columns alone cannot answer equivalent queries. These are separate capabilities: a confidence number alone would not recover method or actor. No surveyed source establishes a quantified retrospective migration cost; the only verified later addition here is SSSOM's set-level confidence field.

## WHAT I DID NOT SEARCH

- Internal source trees, schemas, tests and the existing sixteen clearinghouse tables: deliberately excluded by task scope. No local production test suite was run for this documentation-only external deliverable.
- GTDB release files or the supplied disappearance measurement (7,225 / 596,859): accepted only as requester context, not independently verified. A missing record can reflect selection/release differences, not necessarily retraction; no GTDB reason classification was measured.
- KBase/BV-BRC MD5 canonicalization, provenance record and workspace-ref version semantics: not inspected. No claim is made that these digests identify the same canonical object as the internal SHA-256.
- Full UniProt `idmapping.dat` download and live mapping multiplicity census: not performed. Browser could not open its FTP README; direct HTTPS timed out. The three-column shape is verified from the original service publication instead.
- NCBI browser-tool access to FTP README URLs failed; direct Python HTTPS succeeded for Gene and assembly summary documentation. No whole NCBI cross-reference datasets were downloaded. Documentation, not a pinned release dataset, supports the schema/algorithm statements.
- First guessed InterMine raw XML paths returned 404. GitHub's external tree API located `bio/model/core.xml`, which was successfully read; see the pinned schema citation in the survey. No live InterMine deployment or current resolver behavior was tested. The resolver documentation is an older version.
- `curies` documentation opens failed despite searchable snippets; its raw upstream README was successfully fetched. `prefixmaps.readthedocs.io` failed, but the official LinkML-hosted docs succeeded. A guessed Bioregistry usage page and SSSOM slot URL failed; the API reference, model docs, specification and repository were used instead.
- No evidence of Ensembl regretting this schema, no verified chronology/cost for retrofitting its `info_type`/`info_text`, and no measured cost for SSSOM's later confidence-related addition. “They regretted it” would be an unsupported claim.
- No measured corpus-size/organizational threshold for replacing an application tuple with a registry; no demonstration that Identifiers.org or Bioregistry evolved from such a tuple. Their existence alone does not establish that history.
- No measured benchmark specifically partitioning identity crosswalks by vocabulary, no local lakehouse experiment, and no verified source-specific skew statistics. General primary engine documentation is the basis for the partition discussion, not a crosswalk war story.
- No broad vendor comparison of identity-graph/entity-resolution products, paid analyst material or paywalled-only evidence. Reltio is the concrete MDM sample; Ensembl, UniProt, NCBI, GO/OBO and SSSOM supply the biological/mapping evidence. No production incident postmortem was established.

Confidence: **high** in documented schema/lifecycle distinctions and the counterexamples to universal scalar inversion; **medium** in workload recommendations and tool fit. Per-source cardinality contracts, release-pinned mapping samples and an Iceberg file/latency benchmark would raise confidence in application-specific conclusions.
