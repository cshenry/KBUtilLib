## STALL REPORT (the binding part)

Recommendation: do not start the overnight implementation from this PRD. Resolve the ownership, lock, and retry contradictions first. These are execution blockers, not requests for nicer documentation. The numbered sequence below follows dependencies: config, locks, worker scheduling, batching, then acceptance. Quoted PRD references refer to the inlined fullprompt.md unless otherwise stated; that PRD and its referenced taskplan are not present at the requested topic directory in this checkout.

1. **PHASE / MODULE: Queue configuration — resolving a seat to an account.**
   - **DECISION I CANNOT MAKE:** “every named seat must exist in some declared profile's roster shape” and “queues whose seats resolve to that account” do not specify which profile supplies that resolution. The promised invariant is “no account can be over-committed.”
   - **WHY IT STALLS ME:** Seat names are not globally bound routes. Profiles map names to model aliases, and `roster()` allows per-job alias overrides and replacement of the entire proposer bench (`src/kbutillib/domains/ai/council/config.py:657`, `:728`, `:756`). A queue serving `proposer_1` can therefore serve different accounts in simultaneous jobs, including persisted jobs created under an older config. Validating only the default profile makes the safety promise false; rejecting all such profiles or overrides removes existing supported behavior without authorization. Endpoints sharing an account can also declare different caps; today's worker uses their minimum (`src/kbutillib/domains/ai/council/engine/worker.py:362`).
   - **RECOMMENDED RESOLUTION:** Add: “In queue mode, resolve every declared profile and charge each queue's full concurrency × workers reservation to every account it can reach; an account's cap is the minimum effective endpoint cap for that account. At submission and before claiming existing jobs, reject any roster or override whose seat/account/backend mapping falls outside that validated set, with a diagnostic naming the job and seat; leave existing calls untouched.”

2. **PHASE / MODULE: Queue configuration — ownership coverage and multi-account queues.**
   - **DECISION I CANNOT MAKE:** Validation prohibits duplicate seats but does not require coverage. `roles` can further exclude calls. Story 9 says “my concurrency budget [covers] exactly one account,” but the implementation calls one account per queue merely “the normal configuration.”
   - **WHY IT STALLS ME:** A valid-looking config can omit meta, filter out a required role, or combine seats from multiple accounts. Does the daemon reject it, run a fallback worker, or knowingly leave jobs stuck? For an allowed multi-account queue, is `concurrency` an aggregate queue limit or a separate allocation for each account? The current worker builds full account capacities, not a queue-level cap (`src/kbutillib/domains/ai/council/engine/worker.py:362`). These choices change both liveness and provider load.
   - **RECOMMENDED RESOLUTION:** Add: “Queue mode requires exactly one owner for every executable (seat_name, role) in every accepted job roster, with no implicit fallback worker. Every queue must resolve exclusively to one account across its accepted rosters; reject uncovered pairs and multi-account queues. Each child gets queue.concurrency slots, not the account's full max_concurrency.”

3. **PHASE / MODULE: Queue/batch configuration — incompatible defaults and configuration scope.**
   - **DECISION I CANNOT MAKE:** QueueConfig declares “batch_size … Default 1,” while Q3 says “20 by default, 50 as the configurable maximum.” Elsewhere “A seat may declare batch_size,” although the only specified field lives on a queue that can contain several seats.
   - **WHY IT STALLS ME:** I cannot implement one default that meets both statements. Choosing 20 changes existing invocation behavior and spend; choosing 1 contradicts the supposedly binding DECIDED line. Inventing a seat-level override creates an undocumented precedence rule, especially for the combined critic/meta queue.
   - **RECOMMENDED RESOLUTION:** Replace Q3's decision with: “QueueConfig.batch_size defaults to 1 and accepts integers 1 through 50; 20 is the recommended explicit opt-in value for Claude queues. This version has no seat-level batch_size field; a queue's value applies independently to all its seats.”

4. **PHASE / MODULE: Execution locking — multiple workers cannot take the specified lock.**
   - **DECISION I CANNOT MAKE:** Workers take “their own partition lock exclusively” with filename “council-<queue>.lock,” but the daemon launches “workers children for a queue declaring more than one.”
   - **WHY IT STALLS ME:** All children of that queue contend for the same exclusive lock. Only one can start. Replacing the lock with a shared one permits duplicate queue launches and invalidates the static concurrency reservation. The current single-holder record/probe API cannot represent multiple shared holders either (`src/kbutillib/domains/ai/council/execlock.py:114`, `:174`). Choosing worker identities and controller exclusion is now a correctness decision.
   - **RECOMMENDED RESOLUTION:** Add: “Use one persistent exclusive controller lock per store and one exclusive worker lock per (queue_name, worker_index), indices 0..workers-1, held alongside the store shared lock. Keep holder metadata in the worker lock files; store-wide refusal enumerates all kernel-held worker locks. Controller startup and per-queue start are serialized and may never create a second child for an occupied index.”

5. **PHASE / MODULE: Execution locking — unpartitioned and mixed-config execution breaks the account guarantee.**
   - **DECISION I CANNOT MAKE:** “Worker kinds (daemon, run) take the store-wide lock in shared mode,” and “A config declaring no queues behaves exactly as today.” No partition identity or coexistence policy is defined for unpartitioned `run`, an old-style daemon, or two queue configs with different names.
   - **WHY IT STALLS ME:** Static config validation counts only one config's reservations. A second process using another config, or an unpartitioned run using the whole account cap, can acquire nonconflicting partition locks and oversubscribe the account. Today's exclusive lock prevents that. Independent claim tokens do not prevent provider overcommit. Renaming the existing `daemon.lock` to the proposed `council.lock` also lets an old binary and a new binary miss each other's locks (`src/kbutillib/domains/ai/council/execlock.py:55`).
   - **RECOMMENDED RESOLUTION:** Add: “Retain daemon.lock as the store-wide lock inode. Unpartitioned run/daemon and evaluate remain exclusive. Shared queue workers are launched only under the unique store controller, whose active queue configuration is immutable until all its workers stop; standalone run in queue mode is refused. A changed queue config requires stop-all followed by start-all.”

6. **PHASE / MODULE: Daemon supervision — launch versus ongoing supervision.**
   - **DECISION I CANNOT MAKE:** The daemon “supervises one worker process per queue,” but the specified implementation only has `start()` launch detached children. Story 6 requires death recovery; per-queue stop must persist while siblings run. No surviving supervisor, restart policy, or failure-of-start behavior is specified.
   - **WHY IT STALLS ME:** Today's detached child is the daemon itself, with the caller exiting after verifying its lock (`src/kbutillib/domains/ai/council/daemon.py:411`). Merely spawning N detached daemons provides no process to restart them. An automatic restart can undo an intentional queue stop; no restart can leave an overnight job permanently unserved. If the third child fails startup, leaving the first two consuming work or rolling them back are materially different outcomes.
   - **RECOMMENDED RESOLUTION:** Add: “One detached controller remains alive to supervise workers. Unexpected worker exits trigger claim recovery under the existing stale-worker lease and restart after 5 seconds, indefinitely, with failures visible in status; deliberate per-queue stop disables restart until explicit start. Initial start is all-or-nothing: if any child fails readiness, drain and stop every child started by that operation and return failure. Foreground mode runs this same controller attached to the terminal.”

7. **PHASE / MODULE: Worker claiming and batch assembly — conflicting capacity units.**
   - **DECISION I CANNOT MAKE:** `_claim` requests “at most that account's free slots” and must release rows at capacity, while “A batch is one in-flight unit … not N” and `n` is assembled from `len(claimed)`.
   - **WHY IT STALLS ME:** At concurrency 1 the specified claim bound yields one row forever: a configured batch of 20 never forms. At concurrency 8, per-row assignment prevents a 20-row batch. Claiming 20 rows without first grouping them can conversely create many one-row invocations across jobs/seats. The current loop assigns and launches one task per claimed row (`src/kbutillib/domains/ai/council/engine/worker.py:799`, `:901`, `:937`). I must change the literal claim limit or violate the batch accounting rule.
   - **RECOMMENDED RESOLUTION:** Add: “For batched queues, free capacity is measured in invocations: claim up to free_slots × effective_batch_size candidate rows, group by the complete homogeneity key, and schedule no more than free_slots batches. Release surplus groups without incrementing attempts; assigned increments once only when a batch is reserved. Unbatched claims retain the free_slots row bound.”

8. **PHASE / MODULE: Batched invocation — output ceiling is neither enforced nor total.**
   - **DECISION I CANNOT MAKE:** The PRD promises “a batch can never be sized into output truncation,” using `floor(seat.max_output_tokens × 0.75 / per_item_output)`, and requires measuring whether Claude “honours” the limit. It specifies no behavior when that floor is zero.
   - **WHY IT STALLS ME:** Neither CLI argv currently forwards `max_output_tokens` at all (`src/kbutillib/domains/ai/llm/apis/cli.py:114`, `:344`); the Claude question is not just whether an existing argument is honored. A backend support declaration does not establish an output cap. A running mean is not a worst-case bound even with a real cap. Zero yields an empty batch and can leave work spinning forever. Guessing a supported provider option, or treating a desired seat limit as observed backend capacity, risks the truncation the design claims to prevent.
   - **RECOMMENDED RESOLUTION:** Add: “Enable batching only for a CLI/model combination with a verified effective output cap and documented configuration mechanism; until verified, force that combination to singles and report why. Use the lesser of that cap and seat.max_output_tokens in the heuristic. If derived_ceiling is below 1, refuse batching for that seat with a config/runtime diagnostic rather than assembling an empty batch. This heuristic reduces truncation risk; detected truncation still follows bisection.”

9. **PHASE / MODULE: Batched settlement — malformed individual answers lack a policy.**
   - **DECISION I CANNOT MAKE:** The PRD specifies missing, unknown, duplicate elements, and “schema-invalid at the top level,” but says only that each returned element is validated against the existing role schema.
   - **WHY IT STALLS ME:** One element can have a valid key and an invalid role answer while the other 19 are valid. Validating the entire wrapper schema rejects the whole batch; validating elements separately leaves the bad row's retry-versus-terminal behavior undefined. The current `_invoke` makes schema-invalid single replies terminal (`src/kbutillib/domains/ai/council/engine/worker.py:1198`). Missing elements are always “released for retry with its attempt count incremented,” with no exhaustion rule. An always-omitted item could therefore consume calls indefinitely.
   - **RECOMMENDED RESOLUTION:** Add: “Validate the wrapper structure and keys separately from role payloads. Bank every valid unique known answer. Treat a keyed invalid payload like a missing answer: record invalid_output and release only that row with increment_attempt=True while below max_attempts; otherwise settle it as error and advance its item. Apply the same finite max_attempts rule to missing answers. Remove item_key before existing role-schema validation.”

10. **PHASE / MODULE: Bisection — retry exhaustion contradicts isolation.**
    - **DECISION I CANNOT MAKE:** “Bisection depth consumes one attempt per item” and “recursing to single items” must coexist with “A single item that fails alone fails as it does today” and the test that “the other items settle.”
    - **WHY IT STALLS ME:** Today's default max_attempts is 3 (`src/kbutillib/domains/ai/council/engine/worker.py:282`, `:1223`). With a poison item in a 20-row batch, a path 20→10→5→3→2→1 needs five failed ancestors before the single-item invocation. Honoring the current budget can fail healthy neighboring rows before isolation; ignoring it contradicts the attempt budget. Retrying split rows through the ordinary queue can also recombine them with the poison item. Attempt numbers are derived from attempt_count and are a primary key, so recursion needs real counter updates (`src/kbutillib/domains/ai/council/engine/worker.py:1621`; `src/kbutillib/domains/ai/council/store/schema.py:290`).
    - **RECOMMENDED RESOLUTION:** Add: “Record and increment attempt_count for each failed ancestor invocation, but do not enforce the single-item max_attempts budget until a row is invoked alone; count singleton failures separately from batch-isolation failures. Within a live worker, run split halves directly under the existing claims, sequentially per reserved slot, without reassembling them. On worker death, abandon the split tree and recover claims without an additional failure charge. Persist enough attempt metadata to reconstruct singleton failures across restarts.”

11. **PHASE / MODULE: Batched usage and ceiling feedback — failure costs and missing anchor.**
    - **DECISION I CANNOT MAKE:** Usage is “recorded once on the batch's first call row … remaining rows record a zero-cost attempt referencing it,” but settlement is independent, and bisection generates multiple paid invocations for the same rows. “Running mean of observed per-item output” is not defined for missing or malformed replies.
    - **WHY IT STALLS ME:** The first row may be missing, invalid, or stale; a child batch may have the same first row as its parent. Today's failed and retried attempts discard result usage, while successful settlement increments endpoint tokens inside the row settlement transaction (`src/kbutillib/domains/ai/council/engine/worker.py:1394`, `:1491`, `:1520`). Blindly reusing these paths loses failed-batch spend, double-counts costs on reprocessing, or references an attempt that was never written. Including zero-cost member attempts in the mean drives the output estimate artificially downward and enlarges unsafe batches.
    - **RECOMMENDED RESOLUTION:** Add: “Identify each backend invocation by a unique invocation_id. Atomically record its reported usage, ordered member ids, batch size, and anchor (call_id, attempt_no), and update endpoint spend exactly once, independently of which answers settle; do this for failed invocations too. Every member attempt references invocation_id; zero-cost references are excluded from output estimation. Derive the mean as total completion_tokens / total requested members over successful complete invocations for the same seat, role, and served model; exclude partial, truncated, failed, reused, and unknown-usage samples. Start with configured estimates or fresh singleton observations when no eligible history exists.”

12. **PHASE / MODULE: Accuracy acceptance and live CLI validation.**
    - **DECISION I CANNOT MAKE:** Q2 says “gate the full-corpus run on a measured sample A/B,” story 20 asks for an “accuracy comparison,” and t8 “must measure” CLI behavior before trusting the default. No sample definition, labels/reference, pass threshold, run budget, or exact deliverable is specified; the referenced t8/t10 taskplan is absent here.
    - **WHY IT STALLS ME:** Agreement with the old unbatched run is not accuracy against truth. I cannot invent a scientific acceptance criterion and then claim the release gate passed. Access failure also leaves it unclear whether code completion is allowed with batching disabled, or whether the overnight build must stop. The production corpus resume is explicitly out of scope, so it cannot be used to discover the answer after spending the full run.
    - **RECOMMENDED RESOLUTION:** Add: “Code may land with batching opt-in disabled when live measurements are unavailable. Produce a reproducible A/B report on 100 fixed-seed sampled go_mf items, covering critic and meta using identical frozen upstream context, and compare normalized per-role decisions between singleton and batch-20 runs; report disagreement, validity, latency, and measured usage. This measures agreement, not accuracy unless reviewed labels are supplied. Do not authorize the corpus run automatically: an operator must approve this report and the measured CLI cap before enabling batching for that run.” If an automatic overnight acceptance is required instead, the author must supply labeled data and a numerical pass threshold; neither is derivable from this repo.

The additive nullable queued_at change, per-seat SQL predicates, preservation of single-item prompt hashes, stdin-file plumbing, and existing event-driven review creation have no independent specification blocker after the decisions above. Index installation and CLI temp-root naming are ordinary implementation choices, not reasons to halt.

## FREE CRITIQUE (non-binding)

- **Evidence and verification limits.** I inspected the current config, worker, daemon, lock, schema/migration, query, and CLI implementations cited above. Attempted `python -m pytest tests/domains/ai/council/test_execlock.py -q --disable-warnings --maxfail=1`; the task interpreter returned `No module named pytest`, so no runtime tests executed. No production database or live paid CLI calls were used, and the PRD's production numbers and claimed stdin root cause were not independently confirmed. Confidence is high in the source-level contradictions, medium in completeness; a runnable test environment and the absent taskplan would raise it.

- **The PRD overstates its causal evidence.** “Nothing about the models was the problem” in humanprompt.md sits beside 23/24 Claude transport failures and one usage observation. The code plausibly permits a pipe-feeding stall, but a correlation is not a measured event-loop-blocking diagnosis. Verify the file-input correction under deliberate loop blocking and actual host load before attributing the failure mechanism conclusively. Do not broaden billing-sensitive argv changes as part of that experiment.

- **A queue is not necessarily a seat.** “Homogeneity is free … a partitioned worker's claim is already single-seat” is false for the explicitly required combined critic/meta queue. Even a one-seat queue can claim multiple jobs and query versions. Grouping by the complete key must precede batching; an assertion over the entire claimed list will crash on normal review traffic. The grouping key is already specified, so this is a dangerous implementation trap rather than a missing decision.

- **Per-account claiming is possible without new account columns.** Resolve account→endpoint sets from worker configuration and use the store's existing endpoint filter with seat/role filters. Do not add a guessed account column to call rows. The account should also scope readiness-filter accounting so `_DaemonWorker._claim` does not decrement once per member after assignment changes to once per batch (`src/kbutillib/domains/ai/council/daemon.py:246`).

- **The new index needs an existing-store installation path.** “No schema migration is required” is narrowly true for the seat predicates, not for adding the index to deployed stores. Current same-version `migrate()` only adds missing additive columns (`src/kbutillib/domains/ai/council/store/sqlite.py:352`, `:457`). Metadata declaration alone does not install an index on the already-existing calls table. Add an idempotent index-creation step under the exclusive migration lock; no version bump is necessary. The nullable queued_at DDL must likewise run before workers, not opportunistically under their shared lock.

- **Queue status needs durable ownership.** Workers currently register endpoints, not queue and index (`src/kbutillib/domains/ai/council/engine/worker.py:873`). Endpoint-based liveness will falsely report a stopped codex chair as served because its sibling uses the same endpoint. Apply ownership to status/blocker queries, readiness scans, and until-idle calculations, not only claim selection. Define claimed as all held member rows and in-flight as backend invocations so batch counts remain intelligible.

- **Batch metadata must survive reuse and mixed histories.** Put invocation references in structured attempt metadata or a dedicated relation; do not make the existing token dictionary the only undocumented storage contract. A reused answer should not inherit the original batch's entire spend as fresh cost. Historical NULL queued_at rows cannot be used as service-only latency samples; reused or permission-parked calls never acquired a provider slot and should not fabricate a queue timestamp.

- **Mean-based ceilings are heuristics.** A distribution shift or one long answer defeats a mean regardless of the 25% margin. Measure role/model-specific tails, include wrapper overhead, and record the actual effective cap. The critic's larger input also raises a context-window issue that an output-only ceiling does not address; oversized requests should fail diagnostically and split, with bounded retries.

- **File input adds a file to the supposedly empty cwd.** `run_cli` explicitly promises a “fresh, empty working directory” to prevent project context injection (`src/kbutillib/domains/ai/llm/apis/cli_common.py:713`). Use an innocuous private filename and restrictive permissions; verify no CLI auto-context behavior reads it a second time. Specify a config key such as endpoint `cli_temp_root`, preserve the current default when absent, and pass it explicitly into both CLI backends; changing child TMPDIR alone does not configure the parent TemporaryDirectory.

- **“Bit-for-bit today's behaviour” is too strong.** Budget fixes, different timestamps, file stdin, and batch prompts potentially affect the unpartitioned path. For batch_size=1 preserve the existing user/system/schema format, not a one-element answers wrapper, to protect stored prompt hashes and avoid an accidental opt-in. Add regression coverage for per-job permission gating and single-flight reuse before spending tokens; both currently occur before invocation (`src/kbutillib/domains/ai/council/engine/worker.py:1040`).

- **The concurrency test plan misses the biggest new risks.** Test workers>1 for a single queue, queue-concurrency below account cap, mixed-profile jobs, override rejection, intentional stop versus crash restart, partial startup rollback, and unpartitioned/partitioned exclusion. Test bisection with 20 members and the actual default max_attempts=3, with restart between splits, and with an invalid first answer carrying the usage anchor. Proving claim-token exclusivity alone says nothing about account safety or controller correctness.

- **Keep the corpus resume out of this task.** “Expect the resume itself to be the acceptance test” conflicts with the caution warranted by paid persisted answers. Use a disposable store copied or constructed with production-shaped rosters, stale claims, and reuse records first. The operator's later resume should validate an already-tested path, not discover the multi-process settlement design.
