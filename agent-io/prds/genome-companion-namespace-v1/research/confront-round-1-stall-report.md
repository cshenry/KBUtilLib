## FREE CRITIQUE (non-binding)

- **Evidence and limits of this review.** This is a source/document execution review against the supplied inline PRD and current KBUtilLib checkout. I inspected the actual sharder key/range/Parquet code, BERDL load contract, bootstrap DDL adapter, parameter validators, council archive/current projection/recovery and live-test setup. File inventory searches confirmed the named council PRD and KBDL source files are absent here. I did not query live BERDL, fetch private KBDL objects, or validate the report's live row counts; those are assertions in the PRD, not measurements made during this review. No production code/configuration/schema was modified. Existing tests were not run because the deliverable changes documentation only; the disputed behavior is absent specification, not a failing implementation that a unit test can settle.

- **The document calls uniform-hash partitioning useless, then describes a useful hash-prefix partition.** Equality predicates can benefit from a known deterministic partition derivation even when values are uniform. The current library's inability to express a transform is a practical boundary; it is not proof that bucket partitioning has zero pruning benefit. This does not force changing the selected bare-column partition design. It does mean Q3's rationale should not teach the wrong principle. The real question is measured final-file pruning after supported ingestion, not the elegance of the bronze sorter.

- **A “bounded number” needs a scope.** Even perfect ordering within each delivery does not bound all-history reads as new snapshots/builds arrive. Snapshot-versioned data multiplies storage and file ranges. A current projection can restrict reads, but the benchmark must use that same predicate and show scanned files/bytes, not only wall-clock latency or bronze file counts. Rehearse skewed genomes, multiple annotation runs per gene, and multiple deliveries; a uniform distribution of genome IDs does not imply uniform gene/annotation volume.

- **Physical claims exceed what the helpers promise.** The sharder bounds row buffers and splits skew; it does not guarantee one exact-sized file per range. Its own docstring says the target is conventional, not measured (`src/kbutillib/domains/kbase/berdl/clearinghouse_shard.py:127`). Sparse-column cost depends on encoding, compression and metadata; “nothing else” is too absolute, especially when the actual Parquet call supplies no explicit codec. These are secondary measurement issues once item 14 supplies a real acceptance test.

- **Do not accidentally inherit the sharder's silent winner semantics.** Clearinghouse identical entities and latest result slots have domain-specific dedup rules. Companion coordinates, raw identifiers and experimental observations are not those domains. Conflicting duplicate keys should fail with source evidence, rather than be resolved by lexicographic payload order. The existing `_key_spec` tie-breaks are useful machinery, not a scientific conflict policy (`src/kbutillib/domains/kbase/berdl/clearinghouse_shard.py:5344`).

- **The assembly equality assertion deserves golden tests.** Cover reordered contigs, changed headers, duplicate identical contigs, lowercase/whitespace, empty contigs and representation-only recompression. Test rule A using the shared implementation rather than duplicating normalization logic. The source claim that three assemblies match A is valuable but does not verify every KBDL object-storage digest convention.

- **Caller zero-hit coverage does not fully answer the opening scientific question.** A package run is not automatically proof of coverage for every RNA feature type. The extraction/read documentation should say which feature classes each caller/version detects. Do not interpret a generic caller row as evidence that a tRNA-specific search ran unless that capability is known. Retained-zero and raw-zero counts also differ; the binding amendment makes that difference explicit.

- **Durable aliases need correction semantics eventually.** Provenance lets a reader identify a bad row; it does not retract it. Highest snapshot sequence is not sufficient if two contradictory aliases occur in one snapshot or if distinct identifiers are both legitimate. Append-only retraction/correction events are a future design need. This PRD can ship without them if it does not promise that every old alias remains authoritative forever.

- **Two missing-source cases deserve fixtures before scale testing.** A valid registry row whose JSON/FASTA object is absent must fail delivery verification, not disappear from counts; an annotation job pointing to an older structural build must either map to that build or remain quarantined, never attach to the newest one. Both failure modes can make apparently reconciled row counts look convincing.

- **Operational receipt semantics should include integrity, not only counts.** Equal row counts do not detect wrong build attachment, duplicate-and-missing substitutions, or a bad tool mapping. The council precedent's deterministic inventory/digests and ambiguous-append checks are stronger than the proposed bare `rows_expected = rows_written` shape. Completion tests should deliberately simulate success followed by lost acknowledgement, partial-table commit, restart from a different namespace/schema, conflicting snapshot sequence, and concurrent retry.

- **Several apparent defects are merely stale prose and are not separate stalls.** “Seventeen tables” in the human summary conflicts with eighteen science tables plus two operational tables in the body. Q7 says six named columns while listing seven; Q8 still says per-genome where the authoritative table sections say per-build; multiple Q-number references point at the wrong subject. Use the explicit table inventory and build-scoped table definitions where unambiguous. Fixing these counts/cross-references alone would not make the design executable.

- **The mutable-pointer gotcha overstates automatic query behavior.** Flipping `is_current` changes only queries that actually use it. A notebook reading raw `gene` without a build join will see additional rows after appends, not magically switch gene sets because a boolean changed elsewhere. This is why a supported read projection is substantive functionality, not documentation polish.

- **The ownership boundary is sensible but creates a real availability dependency.** Sequence-free companion tables are a coherent choice. “Loadable” and “publishable” should remain distinct: a missing clearinghouse entity/sequence should be visible as unresolved dependency and should not masquerade as a biological absence.
