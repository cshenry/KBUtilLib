## STALL REPORT (the binding part)

The implementation must stop before production loading: the task graph does not produce an end-to-end loader, and the request/ledger model cannot publish a re-request or safely recover a partial write as specified. The numbered items follow taskplan execution order; parallel tasks are ordered by their first phase. Quoted task identifiers refer to the embedded taskplan. This review uses the supplied live measurement as fact; it did not repeat live queries. The missing PRD bundle and sibling repositories in this checkout are not findings.

1. **PHASE / MODULE: P1 `gc2-1-berdl-smoke`.** **DECISION I CANNOT MAKE:** The smoke is allowed to “SKIP cleanly when credentials are absent,” yet “Every later phase depends on it” and it must “REPORT” whether views work. **WHY IT STALLS ME:** A skipped test establishes neither timestamp round-trip nor view capability; proceeding chooses a projection implementation on no evidence, while treating skip as success defeats the real-dependency gate. **RECOMMENDED RESOLUTION:** “A skipped or inconclusive smoke is a blocked dependency, not a passed gate; persist the endpoint, test result and view capability, and permit subsequent phases only after a live pass.”

2. **PHASE / MODULE: P2 `gc2-2-extend-content-heads`.** **DECISION I CANNOT MAKE:** The task demands “table_configs() still returns 16 configs” while Revision 2b says “21 configs, 'alias' is a fourth kind.” The actual generator documents 21 ([clearinghouse_schema.py:575](../../../../src/kbutillib/domains/kbase/berdl/clearinghouse_schema.py#L575)). **WHY IT STALLS ME:** The stated test cannot pass alongside the existing alias tables and the no-regression requirement; deleting five aliases destroys the very interface the loader requires. **RECOMMENDED RESOLUTION:** “Replace the 16-config assertion with 21 configs, including all five existing alias configs; preserve their exact schemas and partitions.”

3. **PHASE / MODULE: P2 content metrics and `gc2-3-kbdl-result-types`.** **DECISION I CANNOT MAKE:** “assembly_level ... from contig count and closure” specifies four outputs but no mapping; the tests refer to “the documented value” without documenting either value. “gc_content,” N50, ambiguous bases and “a stated tolerance” lack denominator, empty-input, N50 tie/rounding and numeric tolerance rules. **WHY IT STALLS ME:** Independent implementations can write different permanent metadata for the same assembly or emit different disagreement reports. Four catalogue categories cannot all be inferred from only count and closure without an arbitrary policy. **RECOMMENDED RESOLUTION:** “Define a complete truth table for assembly_level including unknown closure and multi-contig cases, GC numerator and denominator including ambiguity and empty assemblies, N50 threshold and rounding, and explicit per-metric absolute or relative CheckM2 tolerances; include golden inputs and expected outputs.”

4. **PHASE / MODULE: P2 protein content, `gc2-3`.** **DECISION I CANNOT MAKE:** “is_fragment is true when the protein has no start or no stop codon” treats a protein sequence as containing DNA codons, and provides no translation table, partial-feature rule, or policy for stripped terminal `*`. The same protein can occur as both partial and complete. **WHY IT STALLS ME:** The value cannot reliably be derived from the bytes of the shared protein entity; choosing from an occurrence writes an occurrence-specific fact fill-only onto a shared sequence and can mislabel every other occurrence. **RECOMMENDED RESOLUTION:** “Remove is_fragment from protein_content; record partial/start/stop completeness per feature occurrence using specified source fields and null when unknown.”

5. **PHASE / MODULE: P2 result type registration `gc2-3`.** **DECISION I CANNOT MAKE:** It requires schemas “REJECTED when a required field is missing” but lists fields without specifying which are required, their types, nullability, ranges, or whether unknown fields are allowed; nor does it specify exact `tag` versus `version` representation for `genome_quality@1`. **WHY IT STALLS ME:** Plausible schemas reject valid historical assessments or accept malformed data, and registry entries may not match result rows. **RECOMMENDED RESOLUTION:** “Publish the exact two JSON Schema documents and registry rows, including required arrays, types, nullability, bounds, additionalProperties, tag and version encoding, and canonical example payloads.”

6. **PHASE / MODULE: P2/P4 task ordering.** **DECISION I CANNOT MAKE:** `gc2-3` has `depends_on: []`, although the testing decisions say “Every later phase depends on” the smoke. `gc2-6` depends only on `gc2-3` although it writes columns from `gc2-2` and aliases whose live bootstrap is outside scope; `gc2-8` depends on `gc2-5` and `gc2-7` but not `gc2-6`, despite “Phases 1 and 2 ... are done ... by gc2-6.” **WHY IT STALLS ME:** The scheduler can execute writes or integration before their schemas and prerequisite writer exist; the alias target is known absent in the supplied fresh measurement, so the stated hard precondition is currently unsatisfied. **RECOMMENDED RESOLUTION:** “Make gc2-3 depend on gc2-1; gc2-6 depend on gc2-2, gc2-3 and an externally verified alias-bootstrap gate; gc2-8 depend on gc2-6 as well as gc2-5 and gc2-7. A missing live alias table blocks loading until the separately owned bootstrap succeeds.”

7. **PHASE / MODULE: P3 `gc2-4` operational schema.** **DECISION I CANNOT MAKE:** `load_request` explicitly includes `request_id STRING`, but “the last FIVE columns of EVERY table” also include `request_id STRING`; only `load_ledger` is told not to duplicate tail columns. **WHY IT STALLS ME:** Literal implementation emits duplicate-column DDL for `load_request`; excluding the request ID from one location is necessary but unspecified. **RECOMMENDED RESOLUTION:** “Declare request_id only in the provenance tail of load_request, as for load_ledger; its logical key remains the tail's request_id.”

8. **PHASE / MODULE: P3/P4 projections.** **DECISION I CANNOT MAKE:** The projection definition says “LATEST” results and “current build,” but does not define quality-result ordering, ties, source precedence, valid currency fallback when zero or multiple builds have `source_designated_current`, or the join/decoded payload mapping from protein/gene results to `function_content`. `gc2-9` says fallback to “the selected build's source_designated_current,” which assumes the selection it must define. **WHY IT STALLS ME:** SQL can multiply rows, pick arbitrary assessments/builds, or attach unrelated functions to features; the stated one-row-per-genome and one-row-per-(feature, tool, function) cannot be checked consistently. **RECOMMENDED RESOLUTION:** “Specify complete projection SQL or an equivalent normative relational algorithm, including result payload-to-function mapping, all join keys, timestamp/null/tie ordering, and fail-closed behavior for zero or multiple source-current builds.”

9. **PHASE / MODULE: P3/P4 projection materialization.** **DECISION I CANNOT MAKE:** “if SQL views cannot be created ... materialized tables rebuilt per request” conflicts with “NO mutable column anywhere,” “NEVER DROP OR REPLACE A LIVE TABLE,” and declarations that can change publication or currency independently of a request. **WHY IT STALLS ME:** Append-only materialized rows cannot remove a previously published genome or replace an old current build, and a per-request rebuild misses later declarations. Readers see stale or duplicate science. **RECOMMENDED RESOLUTION:** “If views are unavailable, specify a versioned projection snapshot and atomic reader pointer, its refresh triggers for receipts and declarations, and safe failure/recovery; otherwise make view support a hard prerequisite and stop if unavailable.”

10. **PHASE / MODULE: P4 `gc2-6` alias and migration.** **DECISION I CANNOT MAKE:** The loader must write “the KBDL G-number, the genome JSON object id, the FASTA object id, the assembly accession,” but the closed genome alias vocabulary contains no G-number source ([clearinghouse_schema.py:342](../../../../src/kbutillib/domains/kbase/berdl/clearinghouse_schema.py#L342), [line 352](../../../../src/kbutillib/domains/kbase/berdl/clearinghouse_schema.py#L352)). Also P2 changes emitted DDL and refuses old columns; P8 says “bootstrap the clearinghouse extension” but no task defines how to evolve the already-existing empty live content tables without dropping or silently accepting them. **WHY IT STALLS ME:** A compliant alias write has no legal source for a required identifier, and an idempotent CREATE IF NOT EXISTS cannot add columns to existing tables. First production load has either invalid aliases or stale schema. **RECOMMENDED RESOLUTION:** “Have the owning alias change add a named G-number source with specified scope and invertibility before gc2-6; define and test an explicit additive ALTER TABLE migration for each existing empty content table, with live zero-row recheck and full post-migration verification.”

11. **PHASE / MODULE: P4 `gc2-6` sequence annotations and identity.** **DECISION I CANNOT MAKE:** “A protein already annotated by a tool AT A VERSION is NOT re-annotated” ignores `parameter_set_hash`, result type/version, database and potentially occurrence context, although results explicitly carry those fields and TRANSYT requires taxonomy. The PRD also demands per-feature tools that ran on a particular build while providing no association between a build/feature and the per-sequence result. **WHY IT STALLS ME:** Same tool/version with different databases or parameters is incorrectly suppressed, and joining every result for a shared protein to every occurrence attributes tools or functions to builds where they did not run. **RECOMMENDED RESOLUTION:** “Deduplicate by the complete result identity including entity, result type/version, source and parameter-set hash, reject conflicting payloads, and define an occurrence/build-to-result provenance relation that records which result applies to each feature; specify how contextual calls are handled.”

12. **PHASE / MODULE: P4–P6 delivery and integration.** **DECISION I CANNOT MAKE:** The body requires a SQLite backup plus object closure, checksummed manifest, deadline and supersession resolution, but no task assigns implementing the delivery producer, manifest validator, durable retry inventory, object traversal or request-to-object selection. `gc2-6` is in KBDL while `gc2-8` is in KBUtilLib; their call boundary, credential/transport ownership and data contract are unstated. **WHY IT STALLS ME:** The separate implementations cannot be wired into the P8 end-to-end verb from task outputs alone; reading a SQLite backup alone silently produces missing features, and a torn or incomplete delivery can be consumed. **RECOMMENDED RESOLUTION:** “Add ordered delivery and integration tasks specifying manifest schema, object closure and supersession algorithms, durable state and deadline behavior, plus a versioned KBDL-to-KBUtilLib API/CLI contract and integration test using a complete and an incomplete delivery.”

13. **PHASE / MODULE: P5 `gc2-7` and P6 `gc2-8` caller provenance.** **DECISION I CANNOT MAKE:** Validator rule 8 says “caller_version ARE MANDATORY wherever the corresponding ... caller is present”; the loader says `'source' has no version` and “A missing historical version stays NULL WITH A RECORDED QUALITY DIAGNOSTIC.” No diagnostic destination is specified. **WHY IT STALLS ME:** Valid historical and source-called features must either fail, lose provenance, or receive invented versions. **RECOMMENDED RESOLUTION:** “Exempt caller='source' and explicitly missing historical caller versions from the version requirement, retain NULL, and specify a durable per-build diagnostic record and reason vocabulary; require a version for all other newly executed callers.”

14. **PHASE / MODULE: P5/P6 keys, build identity and coordinates.** **DECISION I CANNOT MAKE:** `structural_features_digest` “covers EVERY feature and its qualifiers in FEATURE-ID ORDER” without defining the serialized fields, normalization or digest bytes; `assembly_content_hash` and per-build coordinate convention selection/conversion are also unspecified. Many tables lack full logical keys even though validators must reject conflicting “FULL LOGICAL KEY” duplicates. **WHY IT STALLS ME:** Builders can mint different IDs for identical builds, collide incompatible builds, hash the wrong strand or coordinates, or drop legitimate qualifier/caller/consensus rows. Golden vectors authored by each implementer after choosing a rule do not settle interoperability. **RECOMMENDED RESOLUTION:** “Publish normative structural digest preimage schema and golden vectors, assembly_content_hash rule, exact coordinate conversion including strand and bounds for both conventions, and full logical keys for every table, including qualifier, caller, consensus, declarations and request-scoped rows.”

15. **PHASE / MODULE: P6/P7 request idempotence and completeness.** **DECISION I CANNOT MAKE:** “Re-requesting a genome whose content hash is unchanged is a no-op EVEN IN A NEW REQUEST” conflicts with “every row scoped to a load request,” completeness applied to rows' `request_id`, and the rebuild case requiring a second build for the same assembly. The ledger says new-request expected/written may both be zero, but supplies no durable membership mapping from that request to earlier rows. **WHY IT STALLS ME:** A completed second request cannot establish which earlier rows belong to it, and assembly-only no-op can suppress an enriched or rebuilt feature set. A partial retry may also confuse globally existing rows with rows owned by an incomplete request. **RECOMMENDED RESOLUTION:** “Add immutable request-to-genome/build membership with explicit references to the owning reconciled request; deduplicate content globally and builds by build_id, not genome hash alone; define completeness and expected/written counts over those references and new writes, including interrupted and overlapping requests.”

16. **PHASE / MODULE: P7 `gc2-9-consensus-ledger`.** **DECISION I CANNOT MAKE:** A receipt is “written ONLY AFTER reconciliation,” but neither table inventory nor exact independent counting, ambiguous write recovery and lock scope across overlapping requests are defined. The lock is bound to “(request digest, namespace, schema version),” so different request digests can concurrently insert the same global build. `status` is a field on immutable `load_request` without values or transition semantics. **WHY IT STALLS ME:** Lost acknowledgements and parallel requests can produce duplicate rows/receipts or false reconciliation; status cannot transition without violating immutability. **RECOMMENDED RESOLUTION:** “List every receipted table and independent count/digest algorithm, define global-key concurrency and ambiguous-commit recovery for both rows and receipts, and derive request status from immutable receipts rather than updating load_request.”

17. **PHASE / MODULE: P7 curation.** **DECISION I CANNOT MAKE:** “the chain head, following supersedes_curation_id, with a CYCLE GUARD” does not define forks, multiple independent assertions on one feature, cross-feature supersession, missing predecessors or whether different assertion types can supersede one another. **WHY IT STALLS ME:** One arbitrary head can erase a valid independent curation or apply a correction to the wrong feature. **RECOMMENDED RESOLUTION:** “Require each supersession to reference an existing assertion for the same feature and assertion stream; reject cycles and forks, and return one effective head per independently keyed assertion stream.”

18. **PHASE / MODULE: P8 `gc2-11-acceptance`.** **DECISION I CANNOT MAKE:** It requires real zero-hit and never-run callers, a real CRISPR feature, shared-protein annotations, and published projection checks, but identifies no qualifying genomes and simultaneously says “THE LOADER WRITES NO DISPOSITION DECLARATION.” It also asks for an acceptance range “FROM THAT MEASUREMENT” and a query timing comparison without a workload, baseline, threshold, or isolated rehearsal write target; live genome/gene/protein tables are currently empty and append-only. **WHY IT STALLS ME:** There may be no suitable real fixtures, and no projection returns the required rows unless an authorized declaration is made. An exploratory live rehearsal can permanently close the schema window before the measurement intended to inform Q3, and a range defined after measuring cannot independently pass or fail. **RECOMMENDED RESOLUTION:** “Pre-identify and verify qualifying real genome IDs and a bounded search/failure policy; use isolated scratch clearinghouse and companion namespaces with explicit test-only publication declarations; define the workload and layout/size and performance acceptance thresholds before running, and prohibit production loads until the Q3 decision is recorded.”

19. **PHASE / MODULE: taskplan acceptance criteria across all tasks.** **DECISION I CANNOT MAKE:** Some mandatory prompt obligations are absent from their `success_criteria`: for example `gc2-6` omits verifying the missing live alias bootstrap before any writes; `gc2-8` omits its extra-qualifier/rebuild specifics except by opaque reference to “every case listed”; `gc2-9` omits the specified single-writer lock and unresolved-shard publication block. Several other criteria end “tests assert every case listed” without naming externally observable results. **WHY IT STALLS ME:** A task runner or reviewer evaluating criteria independently can mark an unsafe implementation complete, and cross-repository behavior has no explicit integration gate. **RECOMMENDED RESOLUTION:** “Make each task's success_criteria independently enumerate every mandatory externally observable behavior, including negative cases and prerequisites; add an integration criterion proving the full delivery-to-publication path, and retain the base-commit regression comparison on every task.”

P1's scratch-table mechanics, P3's named science columns and P4's parameterized table DDL have no additional independent blocker identified beyond those above. P5's enum rejection, P6's qualifier JSON and overlap requirements, and P7's decision not to invent a production consensus rule have no additional independent blocker identified. P8 remains blocked as described.

## FREE CRITIQUE (non-binding)

- Q9 explicitly accepts collapsing distinct biological genomes sharing an assembly; user story 17 and the testing paragraph still demand they “remain two distinguishable genomes.” Reconcile those claims in the specification even if the decided limitation remains. The test-only fixture cannot demonstrate a capability the design explicitly rejects.
- The zero-hit prose conflates “ran and found nothing” with zero **retained** calls after filtering. A zero retained count does not prove zero raw hits; the PRD itself acknowledges filtering. Rename the interpretation or add raw and discarded counts before consumers make biological conclusions.
- `taxon_id` is described as “currently believed” in fill-only content. A later taxonomy result cannot update that value under the stated policy; consumers may mistake a stale assertion for current taxonomy.
- Per-sequence `gene_content.protein_entity_hash` also deserves scrutiny: the same DNA can translate differently under different genetic codes or partial contexts. A single fill-only pointer is not obviously an intrinsic sequence fact.
- JSON extraction through a SQL view is still JSON extraction at query time; flattening a view gives convenient columns, not necessarily a physical column scan. Time and inspect actual plans before using the projection as a performance claim.
- Physical locality bound of two files per feature-type partition may be fragile across append requests and concurrent writers even if a single ingestion rehearsal passes; test repeated incremental loads as well as the first batch.
- The requested P3 reserved-word acceptance test needs a real Spark/Iceberg CREATE, not merely a pure schema assertion. The P1 table does not contain `end`; incorporate that column into a scratch integration test.
- Source inspection confirms the existing genome/gene/protein heads are unextended ([clearinghouse_schema.py:398](../../../../src/kbutillib/domains/kbase/berdl/clearinghouse_schema.py#L398)); the supplied fresh measurement, not a new query, establishes the live zero-row window. No tests were run: this deliverable changes no production code, and the relevant PRD and taskplan were supplied inline.
