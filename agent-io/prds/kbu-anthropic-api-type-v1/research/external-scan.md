# External scan: native Anthropic Messages provider

Recommendation: normalize usage exactly once, at the native provider boundary, to `prompt_tokens = input_tokens + cache_creation_input_tokens + cache_read_input_tokens` and `completion_tokens = output_tokens`. Preserve the three input categories separately for pricing. Give spend exhaustion a terminal error classification before applying HTTP-status retries. Scope pacing to the credential's organization/workspace and configured model-class bucket, with shared coordination across worker processes.

These are design recommendations, not findings about KBUtilLib. No local project source was read. Research date: 2026-10-29. “Verified” below means source/document inspection; issue reports are explicitly attributed and were not reproduced against live services.

### 2. Concrete failures: this is not a hypothetical interoperability risk

- **Exact field-name mismatch:** [LiteLLM #28354](https://github.com/BerriAI/litellm/issues/28354) reports `AnthropicResponsesStreamWrapper._process_event` reading `usage.cache_read_input_tokens` from an OpenAI Responses usage object. The actual field was `input_tokens_details.cached_tokens`; the fallback returned zero. The issue's closing comment identifies fix `ed366aa`, PRs #34957/#36057, and regression coverage for streaming/non-streaming paths. Verified the issue and resolution report, not the fix by execution.
- **Entire input/output usage becomes zero after double normalization:** [Hermes #123157](https://github.com/NousResearch/hermes-agent/issues/123157) reports auxiliary adapters producing `prompt_tokens/completion_tokens`, then `moa_loop._price_reference_response` selecting Anthropic/Codex native usage parsers using provider identity. Those parsers look for `input_tokens/output_tokens`; all advisor usage and cost becomes zero. The report includes deterministic reproduction at `7b761da2de`. This is particularly relevant: after normalization, retain the normalized schema identity rather than interpreting the object again as native usage.
- **Historical cache-total undercount:** [Vercel #9921](https://github.com/vercel/ai/issues/9921), closed through #10975 for v6, documents mapping Anthropic's uncached input directly to total input: 18 reported instead of 2,302 for 2,284 cache-write tokens. Current converter above fixes the ordinary three-category case. Verified issue and current source; no release binary was tested.
- **Missing cache-write detail through a shim:** [claude-code-router #1461](https://github.com/musistudio/claude-code-router/issues/1461) reports v2.0.0 OpenAI-to-Anthropic conversion forwarding reads but dropping creation tokens in both response modes. Treat this as a user report, not an independently confirmed current defect.

**Small source-level verification performed:** downloaded external source files to `/tmp/kbu-external-scan`; extracted aisuite's `_get_completion_usage` and LlamaIndex's `get_tokens_from_response` with Python AST, executed them without installing either library, and supplied input=18, cache creation=2,284, cache read=0, output=158. aisuite returned prompt=18, completion=158, total=176; LlamaIndex returned `(18,158)`. Full input should be 2,302 and total 2,460. This verifies those inspected functions undercount cached input; it does not exercise full SDK/network/callback integration. No production files or configuration were changed.

### 3. Token totals, billed cost, and rate-limit consumption are separate quantities

Anthropic explicitly documents `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens`. Its [prompt-caching documentation](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) distinguishes base input, writes, and reads, with reads costing 0.1× base input, five-minute writes 1.25×, and one-hour writes 2×. Those multipliers are prices, not token-count weights. Verified documentation.

LiteLLM's [prompt caching contract](https://docs.litellm.ai/docs/completion/prompt_caching) explicitly includes cache hits in `prompt_tokens` and recommends `completion_cost()` for cache-aware pricing. Its native converter retains write TTL details. Neither its contract nor LangChain/Vercel's inspected converters equates total token volume with invoice cost.

**Design implication (inference):** keep the requested two-key token interface for a volume budget, but label a quote using only gateway-wide rates as an operator-rate estimate. Exact cost requires at least model, uncached input, cache reads, writes by TTL, output, and relevant non-token charges. If an operator deliberately configures a conservative blended rate, that is a pricing policy, not a different definition of `prompt_tokens`. In particular, do not multiply cache reads by 0.1 before passing usage to the volume budget.

### 4. Rate limiting: model buckets and multiple processes

Verified Anthropic documentation: limits have separate RPM/ITPM/OTPM axes; Opus 4.8/4.7/4.6/4.5 share a bucket while Opus 5 and Sonnet 5 are separate. Token-remaining headers round to the nearest thousand; resets use RFC 3339. Combined-token headers can describe the most restrictive workspace limit. Most models exclude cache reads from ITPM. See [rate limits](https://platform.claude.com/docs/en/api/rate-limits).

Concrete production-library prior art:

- **Shared state:** LiteLLM [Router documentation](https://docs.litellm.ai/docs/routing) recommends Redis for production TPM/RPM and cooldown tracking. Its `LowestTPMLoggingHandler_v2` uses per-deployment/model/minute counter keys, checks estimated input against configured limits, and updates usage counters; see [lowest_tpm_rpm_v2.py](https://github.com/BerriAI/litellm/blob/ffcc4f7a70148df3905b6b064857c32b17d3ea71/litellm/router_strategy/lowest_tpm_rpm_v2.py#L600). This is concrete cross-process coordination prior art, **not evidence that deployment IDs automatically aggregate Anthropic sibling models into one upstream bucket**.
- **Header-driven tuning:** [Promptfoo's rate-limit documentation](https://www.promptfoo.dev/docs/configuration/rate-limits/) describes parsing Anthropic remaining-request/token headers and `retry-after`, reducing concurrency below 10% remaining, halving concurrency on throttling and increasing it after sustained success (AIMD). Tracking is described per provider/API key. Its two retry layers are documented separately. This verifies an adaptive concurrency mechanism, not a strict ITPM/OTPM pacer or shared model-class accounting.
- **Staleness explicitly recognized:** [agentpause README](https://github.com/Champoleello/agentpause) describes refreshing stale header telemetry with a small request and configurable Anthropic header names. Useful exploratory prior art, but I did not establish production adoption or multi-process correctness.

**Design recommendation (inference):** use a configurable mapping from model ID to upstream rate bucket; include organization/workspace scope rather than just API-key identity, since several keys can share quota. Keep separate input/output reservations. A Redis-backed atomic reservation service or a single pacing coordinator can allocate capacity across processes; refund/reconcile estimates after responses. If no shared coordinator is available, explicitly divide an operator-configured allowance among a known worker count, with headroom; independently granting the full limit to every process multiplies the aggregate allowance.

**Header pitfalls (inference except documented rounding):** responses are snapshots, can arrive out of order, and cannot account for requests admitted after the snapshot or from other processes. Do not replace shared reservations with an older, larger remaining value. Track observation time, pending reservations and conservative margins. Distinguish concurrency adaptation from token pacing: lowering concurrency does not ensure that several large prompts fit ITPM. Header absence should preserve configured pacing, not imply unlimited capacity.

### 5. Wallet exhaustion needs classification before retries

Anthropic's [rate-limit documentation](https://platform.claude.com/docs/en/api/rate-limits) confirms monthly-cap HTTP 429 uses `error.details.error_code=enforced_spend_limit_reached` without `retry-after`. User/workspace spend limits instead use HTTP 400 `invalid_request_error` and prefixes `You have reached your specified API usage limits` / `You have reached your specified workspace API usage limits`. Verified documentation.

The official Python SDK's `BaseClient._should_retry` checks `x-should-retry`, then HTTP status, including 429, without examining that spend code; `_calculate_retry_timeout` uses retry headers or exponential backoff with jitter. See [src/anthropic/_base_client.py:906](https://github.com/anthropics/anthropic-sdk-python/blob/202db72c87d7c6eaa72129c67ce67fd343a3a20c/src/anthropic/_base_client.py#L906). Thus a spend-cap 429 is retryable by this function unless the server explicitly opts out. This is source-based inference; no exhausted account was called.

[LiteLLM #32785](https://github.com/BerriAI/litellm/issues/32785) documents the analogous OpenAI `insufficient_quota` problem: billing exhaustion and temporary throttling become the same `RateLimitError`. An October comment reports four upstream calls with three configured retries against a synthetic quota-exhausted upstream in v1.103.2. I verified the report, not its current-main status. As positive taxonomy prior art, [LiteLLM-clj's error guide](https://cljdoc.org/d/tech.unravel/litellm-clj/0.3.0-alpha/doc/error-handling) explicitly separates nonrecoverable `:litellm/quota-exceeded` from recoverable `:litellm/rate-limit`.

**Recommendation (inference):** preserve native structured error bodies and response headers; classify the spend code and both documented 400 prefixes before transient retry logic. Do not classify every headerless 429 as exhaustion. Give one layer ownership of retries to prevent SDK × wrapper × task-loop amplification, and propagate a terminal exhaustion result to all workers sharing the affected spend scope.

### 6. Native API versus compatibility shim; SDK versus raw HTTP

Anthropic's [compatibility documentation](https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/openai-sdk) positions its OpenAI surface for evaluation. It documents unsupported prompt caching, ignored tool `strict`, ignored `response_format`, unavailable thinking output, and system/developer messages hoisted into one top-level system field. Unsupported inputs can be silently ignored. These are concrete reasons to implement Messages semantics directly, even when the outward abstraction remains OpenAI-shaped. This does not imply every third-party shim has exactly those limitations.

The SDK is not necessary to normalize usage correctly. Verified current dependency manifest: [pyproject.toml:11](https://github.com/anthropics/anthropic-sdk-python/blob/202db72c87d7c6eaa72129c67ce67fd343a3a20c/pyproject.toml#L11) requires Python >=3.10 and lists `httpx2`, `opentelemetry-api`, `pydantic`, `typing-extensions`, `anyio`, `sniffio`, `jiter`, and `docstring-parser`. This is **current main**, not a claim about older released SDKs or incremental installed size.

**Tradeoff (inference):** raw HTTP can reuse an existing transport and avoid that dependency surface for a small non-streaming backend, but owns protocol headers/version, error parsing, timeouts, connection lifecycle, content-block parsing, and eventual SSE assembly. The official SDK supplies typed models and transport/retry machinery, but still needs application-specific normalization, pacing, and terminal spend classification. Dependency choice does not eliminate these obligations.

## WHAT I COULD NOT FIND

- No independently reproduced live-provider failure or billing experiment. Verification was documentation/source reading plus the two extracted-function checks above; full third-party test suites were not installed or run.
- No verified universal normalization hook shared by all LlamaIndex providers. I inspected its Anthropic integration and core token-counting callback; claims above are deliberately scoped to that accounting path.
- No public OpenRouter server adapter source proving the exact Anthropic/Google translation algorithm. I inspected its public API contract and generated Python `ChatUsage`, not every OpenRouter client language.
- No confirmed mature client automatically discovering Anthropic sibling-model bucket membership from response headers. Searches covered LiteLLM routing/counters, Promptfoo rate-limit docs, Anthropic SDK retry code, and GitHub searches for Anthropic header-based limiters. Shared counters and adaptive concurrency exist, but those do not establish automatic bucket discovery.
- No verified production incident specifically proving out-of-order or stale Anthropic rate headers caused overshoot across processes. Those failure mechanisms and the proposed reservation policy are engineering inferences. Rounding is explicitly documented.
- No verified released client implementation handling the exact `enforced_spend_limit_reached` code found in this scan. I searched that code and spend-limit handling in public clients; the API documentation is authoritative, and the SDK's inspected status-based retry function does not inspect it. I did find analogous quota retry failures and an explicit terminal-quota taxonomy.
- No measured SDK installation size, import overhead, or compatibility assessment against this project's dependencies; doing that would require selecting a released SDK version and inspecting the local dependency environment, outside this external-only scan.

Confidence: **high** for the cited normalization paths and documented mismatches; **medium** overall because current release behavior, distributed pacing, and exact spend-code handling were not integration-tested. A pinned-version mock HTTP suite covering non-streaming/streaming cache usage, terminal spend errors, and concurrent process reservations would raise confidence.
