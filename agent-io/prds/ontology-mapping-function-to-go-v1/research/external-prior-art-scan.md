# External prior-art scan: function descriptions to Gene Ontology

Research date: 2026-10-17. Live web search, primary publications, upstream source, GitHub metadata, and PyPI metadata were available. This is a design research report, not an implementation or an empirical comparison of KBUtilLib rankers. Recommendations and deductions are identified as such; supplied in-house timings were not independently reproduced.

## Summary of findings that bear on the design

- **Recover existing GO annotations and trusted identifiers before ranking text.** GOA already uses curated identifier crosswalks. Preserve EC, InterPro, Pfam, KO, and source provenance from annotation outputs; a product string alone discards useful evidence. GO's KEGG reaction crosswalk and KEGG's KO crosswalk are different resources (§1).
- **Keep Type 1 as the inexpensive fallback and benchmark anchor; do not make Type 2 fitting or equal-weight fusion a prerequisite.** The supplied runtime makes that architecture expensive, and RRF offers no guarantee of improving a stronger component (§3).
- **Evaluate both term linking and annotation quality.** Exact-ID top-1 is useful for a curated linking task, but cannot alone assess a multi-label GO annotation system. Add recall@k, abstention/coverage, and CAFA-style set metrics where complete annotation sets exist (§2).
- **Reuse ontology parsers; evaluate `bm25s` and `ranx` before maintaining substantial retrieval/fusion machinery.** They plausibly replace components, but do not preserve the proposed field weighting, character tokenization, hierarchy policy, or GO-ID tie-break automatically (§4).
- **Test a biomedical bi-encoder plus optional cross-encoder on a held-out product-description corpus.** Embeddings are plausible improvements for paraphrases; current GO text evidence does not establish that they beat this character-BM25 baseline (§5).
- **Version the whole mapping artifact.** Pin ontology, crosswalks, candidate subset, model, and closure policy together; reject obsolete output IDs and distinguish safe replacements from suggestions (§6).

## 1. Prior art in function-text to GO mapping

### Identifier mappings: established infrastructure, not free-text classifiers

GOA's electronic annotation pipeline maps controlled vocabulary identifiers onto GO, retaining evidence and source information. That is distinct from interpreting arbitrary product names. The current GOA overview lists InterPro2GO, EC2GO, UniProt keyword/location mappings, and UniRule among its sources. [GOA annotation methods](https://www.ebi.ac.uk/GOA/ElectronicAnnotationMethods), [current GOA overview and references](https://www.ebi.ac.uk/GOA/newto).

No GO-specific accuracy guarantee. [Source](https://github.com/rsgoncalves/text2term), [2024 paper](https://doi.org/10.1093/database/baae119) |

**Explicit answer to the critical question:** yes—**when a trustworthy structured identifier is available, a curated deterministic cross-reference is the better first-line design choice**. This is an engineering recommendation supported by GOA practice, not a measured head-to-head accuracy result on this project's data. It preserves the upstream evidence, is inexpensive, and avoids reconstructing an identifier from a lossy name. Return all applicable mappings and provenance rather than arbitrarily one GO ID. Check mapping scope, taxon constraints, obsolescence, and contradictions.

GO distinguishes exact, broad, narrow and related synonyms; treating all synonym strings as equivalent evidence can create false specificity. Retain scope in any term index. [GO synonym documentation](https://www.geneontology.org/docs/ontology-documentation/).

Text ranking earns its place for legacy text-only records, missing or unmapped identifiers, variant names and paraphrases, and candidate suggestions for human review. It can also flag disagreements with identifier-derived results. It should not infer an entire complex's catalytic activity merely because a subunit description mentions that complex. “Hypothetical protein” is a legitimate abstention, not a request to find the least bad GO term.

**API recommendation:** retain the simple text-only callable, but offer an adjacent structured-record interface accepting source GO/EC/KO/Pfam/InterPro IDs. Return `method`, evidence/source ID, ontology release, candidate view, and abstention status. This complements the repository's existing accession-description dictionary, which explicitly performs the opposite lookup ([`ontology_dictionary.py:1`](../../../../src/kbutillib/domains/genome/annotation/ontology_dictionary.py#L1)); the current Ontomap utility wraps reaction mapping rather than GO mapping ([`ontomap_utils.py:1`](../../../../src/kbutillib/domains/genome/ontomap_utils.py#L1)).

## 2. CAFA and benchmarking conventions

**CAFA is a protein-function prediction benchmark, not a benchmark of product-string normalization.** Its time-delayed design evaluates predictions against subsequently acquired annotations. It separates GO aspects and distinguishes prediction coverage; input modalities and available prior annotations differ across methods. The naïve frequency baseline is not a lexical baseline. [CAFA overview](https://biofunctionprediction.org/CAFA/), [CAFA3 paper](https://doi.org/10.1186/s13059-019-1835-8).

There is no verified field-wide “achievable text-only accuracy” transferable to these inputs. A concrete caution: the early Text-KNN study reported **62% molecular-function and 17% biological-process cross-validation accuracy**, but classified broad GO categories using abstracts from 36,536 proteins. On actual CAFA targets, binding precision/recall was **0.643/0.17** at the stated 0.95 threshold; catalytic activity was **0.312/0.03**. Those are neither full-GO exact-ID results nor an Fmax estimate for short descriptions. [Study, Tables 2–4 and 7](https://pmc.ncbi.nlm.nih.gov/articles/PMC3584852/); full text was checked through [Europe PMC XML](https://www.ebi.ac.uk/europepmc/webservices/rest/PMC3584852/fullTextXML).

Similarly, GOCat's BioCreative IV GO assignment at five returned concepts obtained standard precision/recall/F1 **0.117/0.157/0.134**, versus hierarchical **0.323/0.356/0.339**. This demonstrates metric sensitivity, not expected KBUtilLib accuracy. [GOCat, Table 2](https://pmc.ncbi.nlm.nih.gov/articles/PMC4154439/).

### Metrics to adopt and what they mean

CAFA3 uses **Fmax**, the best protein-centric precision/recall harmonic mean across thresholds, and **Smin**, the minimum semantic distance over thresholds. Smin minimizes `sqrt(RU(t)^2 + MI(t)^2)`, where RU and MI summarize information-weighted missed and spurious annotations at threshold t. Weighted Fmax and normalized Smin were also reported. This rewards informative correctness rather than merely predicting generic ancestors. [CAFA3 methods and supplements](https://doi.org/10.1186/s13059-019-1835-8).

For reproducible implementations, [`cafaeval` / CAFA-evaluator](https://github.com/BioComputingUP/CAFA-evaluator) supports hierarchical evaluation, weighted statistics, and S statistics using an optional information-accretion file. Its [2024 methods paper](https://doi.org/10.1093/bioadv/vbae043) is a better starting point than inventing approximate equivalents. The package is GPL-3.0-or-later according to its license notice; consider it an evaluation tool rather than silently adding it to this MIT library's runtime.

Information **accretion** uses information conditional on parents; it should not be casually interchanged with raw `-log(term frequency)`, depth, or distance from a root. Freeze the corpus, evidence filters, propagation and parent semantics used to estimate it. Weighted precision/recall weights overlapping and non-overlapping terms; averaging conventions and treatment of zero predictions must be stated. “Weighted PR” without these definitions is ambiguous.

### Critique of the proposed exact-ID / hierarchy / specificity / secondary-MRR scheme

The proposed metrics are useful diagnostics but insufficient as a single release gate. Recommendations:

1. **For description → concept linking**, keep exact-ID top-1, canonicalizing alternate IDs first. Use expert-curated sets of acceptable terms, recall@5/@10, MRR, and precision at a fixed abstention threshold. Top-1 exact-ID is defensible when the intended concept is well specified and the gold standard really identifies it; it is not defensible as the sole metric for all possible biological annotations of a protein. MRR sees the first correct candidate and ignores missing additional functions.
2. **For description → annotation sets**, add per-aspect Fmax, Smin and weighted PR/Fmax, plus a deployed operating point chosen on validation data. Test-set Fmax is a retrospective ceiling over thresholds, not a ready-made production threshold. Raw BM25/RRF scores are not probabilities; cross-query thresholding needs an explicit calibration or rank-cutoff policy.
3. **Keep asserted `is_a` metrics as a named diagnostic**, but do not label them standard CAFA hierarchy evaluation. GO says positive annotations propagate through `is_a` and `part_of`; other relations need their own semantics. Run a separate compatible evaluation using an explicit annotation-safe relation policy. Never compute closure over every edge of `go.obo`. [GO annotation propagation](https://www.geneontology.org/docs/go-annotations/), [relation guide](https://geneontology.org/docs/ontology-relations/).
4. **Specificity is conditional on correctness.** Depth, height, leaf status, and parent count are structural features, not calibrated biological confidence. Report specificity among correct predictions alongside IC-weighted errors; otherwise a very specific wrong child can look better than a correct broad term.
5. **Score both candidate views honestly.** Freeze `specificity_focused` membership and report gold-term coverage and out-of-view targets. An easier restricted universe must not earn apparent gains by removing difficult test cases. For structural metrics, retain ancestors from the reference ontology even if they cannot be returned as candidates.
6. **Prevent circular evaluation.** Partition by normalized description/source family as well as record ID; identical pipeline labels in train and test can exaggerate generalization. Separate curated experimental targets from crosswalk-generated targets, and separate ID-bearing from text-only records. Missing GO annotations are not proven negatives, which also matters to the PU ranker. Report paired uncertainty, per-aspect/source results, cold/warm latency, throughput, peak RSS and artifact size.

The last recommendations are design deductions, not claims that CAFA mandates these exact splits. The central prerequisite is deciding whether the gold set describes **what the string states** or **everything known about the protein**; a text-only mapper cannot recover absent biological context reliably.

## 3. Reciprocal rank fusion

The original method sums `1 / (k + rank)` over constituent rankings. Cormack, Clarke and Büttcher fixed **k=60 during pilot work**, then validated unchanged. Pilot MAP was 0.2145 at k=60 and 0.2147 at k=80, supporting local robustness rather than a universal optimum. On TREC Robust, RRF MAP was **0.3686**, versus **0.3586** for the best individual run. Their experiments generally improved on individual systems and Condorcet fusion, but included exceptions; LETOR CombMNZ was slightly higher without a significant difference. The paper does not prove that adding any ranker helps. [SIGIR 2009 paper, Tables 1–3](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf).

Larger k flattens the contribution of leading ranks relative to deeper ones. Equal untuned weights are a reasonable **training-free baseline**, especially when scores are incomparable and no labels exist. They are not evidence that two components deserve equal trust. Modern lexical/dense retrieval experiments found RRF parameter sensitivity and a tuned convex score combination outperforming RRF, including out-of-domain evaluation. [Bruch, Gai and Ingber, 2023](https://arxiv.org/abs/2210.11934), [published paper](https://doi.org/10.1145/3596512).

**Can a strong plus weak equal-weight fusion hurt? Yes.** There is no monotonic improvement guarantee. A direct counterexample at k=60: relevant A ranks 1 and 100 across two systems; irrelevant B ranks 2 and 1. A scores `1/61 + 1/160 ≈ 0.02264`; B scores `1/62 + 1/61 ≈ 0.03252`. Fusion reverses the correct leading result of the first system. This is a calculation, not a quoted experiment or a claim about Type 2's measured quality. Shared lexical features also make complementary errors uncertain.

| Approach | Advantage | Limitation for this design |
|---|---|---|
| RRF | No cross-system score scale needed; robust baseline | Discards score margins; weak ranker can move strong results; k, truncation and missing-candidate policy matter |
| CombSUM | Adds normalized scores, preserving relative evidence strength | Normalization and weighting need specification; a near-flat/noisy score list can be amplified |
| CombMNZ | CombSUM multiplied by count of systems retrieving the candidate | Rewards overlap; with two complete lists its count factor is constant, adding no discrimination |
| Learned score combination / learning-to-rank | Can downweight or ignore an unhelpful component and use query features | Needs representative labels, leakage controls, validation and retraining policy |

These trade-offs are methodological deductions supported by the formulas, not a universal ranking of fusion algorithms. A learned model can overfit too. For KBUtilLib, gate fusion against **both** constituents, and retain the option of zero weight for Type 2. Sweep k and retrieval depth on validation data; test disagreement cases and compare normalized weighted sums. Preserve candidate view, one-based rank convention, absent-candidate handling, and GO-ID tie-breaking in artifacts. A library's default sort is not proof of the required tie policy.

The supplied 500-query Type 2 gate (~577 s fitting, ~246 s inference, ~4.14 GiB peak RSS) makes improvement per unit cost a necessary decision criterion. RRF itself is cheap; it does not remove the cost of generating its input rankings. No external paper validates those in-house timings or establishes Type 2's incremental accuracy.

**`bm25s` specifically:** it can accept caller-created token lists, so character 3–5-grams are feasible. Its sparse/persisted index could replace slow scoring loops. However, BM25 variant, IDF convention, length normalization, repeated n-grams, boundary handling and tie order must match the baseline if reproduction is required. A weighted sum over separately indexed name/synonym/definition fields is not identical to concatenating those fields or repeating names three times. Benchmark those choices rather than asserting a drop-in replacement. Index construction is corpus preprocessing, even though it requires no supervised fitting. [Upstream documentation](https://github.com/xhluca/bm25s), [technical report](https://arxiv.org/abs/2407.03618).

**`ranx` specifically:** `Run`, `Qrels`, `evaluate`, `compare`, `fuse` and fusion optimization cover much of the ranking experiment harness. Its [RRF function](https://github.com/AmenRa/ranx/blob/master/ranx/fusion/rrf.py#L39) accepts `runs`, `k`, and `name`; it does **not** expose a per-run weight argument there. Do not assume weighted RRF can be configured through that function. Validate missing documents, ties and duplicates against the required contract. Its IR metrics do not replace GO-specific Fmax/Smin, ontology propagation or IC estimation. Dependencies/JIT startup also differ from a stdlib-only baseline. [API and capabilities](https://amenra.github.io/ranx/).

Pyserini additionally already exposes [`reciprocal_rank_fusion(..., rrf_k=60, depth=..., k=...)`](https://github.com/castorini/pyserini/blob/master/pyserini/fusion/_base.py#L30). This is useful if Pyserini is otherwise adopted; adding its retrieval stack solely to avoid a few lines of RRF arithmetic would be excessive.

**Recommendation:** choose GOATOOLS or pronto for robust parsing; use explicit relation-filtered closure; compare `bm25s` with the exact Type 1 baseline; use `ranx` for fusion ablations. Keep optional heavier dependencies consistent with KBUtilLib's existing optional-model pattern ([`ontomap_utils.py:3`](../../../../src/kbutillib/domains/genome/ontomap_utils.py#L3)) and Python >=3.9 declaration ([`pyproject.toml:6`](../../../../pyproject.toml#L6)); latest upstream package compatibility was not installation-tested.

## 5. Semantic and embedding approaches

**A modern bi-encoder could plausibly outperform lexical retrieval on semantic paraphrases, but superiority on these short microbial product descriptions remains unverified.** Chemical substrate distinctions, subunit names, negation, specificity and exact biochemical aliases can make lexical matching very competitive. Treat embeddings as a challenger, not an evidence-free replacement.

### Concrete model families and architecture

- **Sentence-transformer bi-encoders:** encode queries and ontology labels/synonyms/definitions separately, cache term vectors and retrieve by similarity. General models such as [`all-MiniLM-L6-v2`](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2) provide an inexpensive comparison. The biomedical [`S-PubMedBert-MS-MARCO`](https://huggingface.co/pritamdeka/S-PubMedBert-MS-MARCO) is another concrete candidate, though its training task is not GO product-name matching. Its model card specifies CC BY-NC 2.0, so it is a research comparator rather than an unrestricted redistribution default. Model-card performance should not be transferred to this task.
- **Biomedical entity encoders:** [`SapBERT-from-PubMedBERT-fulltext`](https://huggingface.co/cambridgeltl/SapBERT-from-PubMedBERT-fulltext) explicitly aligns synonymous biomedical concepts. Plain BioBERT/PubMedBERT are masked-language encoders, not automatically good sentence retrieval models. SapBERT's original paper reports improvements over such encoders; GO synonym/definition fine-tuning is a plausible next step, not a result established here. [SapBERT paper](https://aclanthology.org/2021.naacl-main.334/), [source/evaluation](https://github.com/cambridgeltl/sapbert).
- **Cross-encoder rerankers:** jointly score a query and each retrieved term's text. [`cross-encoder/ms-marco-MiniLM-L6-v2`](https://huggingface.co/cross-encoder/ms-marco-MiniLM-L6-v2) is a general baseline; biomedical initialization plus task-specific pairs is preferable to assuming MS MARCO supervision transfers. Restrict reranking to a shortlist. [Sentence Transformers architecture documentation](https://www.sbert.net/examples/cross_encoder/applications/README.html).
- **Retrieval-grounded LLM labelling:** retrieve valid GO candidates, supply definitions, then select from that candidate set or abstain. [`OntoGPT`](https://github.com/monarch-initiative/ontogpt) / [SPIRES](https://doi.org/10.1093/bioinformatics/btae104) offers Python extraction with ontology grounding and GO templates; code is BSD-3-Clause. It is a concrete reusable approach, but not proof of calibrated short-description annotation accuracy.

| [ENR GO concept recognition, 2026, Table 2](https://doi.org/10.1093/bioinformatics/btag495) | On MM-GO passages derived from MedMentions, thresholded trained SapBERT-initialized bi-encoder micro-F1 **19.4%**; top-100 retrieval candidate recall **74.6%**; top-100 plus listwise cross-encoder micro-F1 **42.6%** | Passage-level implicit/explicit GO recognition differs from short annotation names. No direct character-BM25 comparison for KBUtilLib; the standalone encoder is not uniformly sufficient |
| [GPTON, 2024 preprint](https://arxiv.org/abs/2410.10899) | Reports accurate text/ontology annotation for **over 68% of gene sets within top five predictions**, using GPT-4 ontology narration | Gene-set labelling is a different input/output task; this is not exact top-1 product-string accuracy |
| [Gene-set LLM evaluation, published 2024 / volume 2025](https://www.nature.com/articles/s41592-024-02525-x) | GPT-4 suggested functions similar to curated GO gene-set names in **73%** of cases | Similarity of generated names is not correct GO-ID assignment or protein-level Fmax |

This is evidence for retrieval plus selective reranking and for careful evaluation, not a definitive 2026 leaderboard for this exact problem. Also distinguish protein-language or sequence/text models such as [ProtNote (2025)](https://doi.org/10.1093/bioinformatics/btaf170), which uses protein sequences and function descriptions, from a text-only callable.

**Suggested experiment:** use the same pinned full candidate universe for Type 1, a biomedical bi-encoder, and the union of their top-k candidates followed by a cross-encoder. Encode individual aliases as well as definitions and deduplicate by GO ID. Measure retrieval recall before reranking, then exact/semantic correctness, abstention, and CPU/GPU cost. Include an exact-name/synonym baseline, identifier-only baseline, hypothetical names, subunits and ambiguous enzyme names. Hold out paraphrase families and upstream annotation sources. Models must be checked for GO/UMLS overlap and release leakage; known-concept alias matching and genuinely new concepts are different tests.

An LLM may generate a valid ID with the wrong biological meaning; identifier validation only eliminates nonexistent IDs. Restrict candidates and retain evidence text, model/checkpoint, prompt and retrieval artifact versions. No retrieved evidence justifies an unconditional LLM fallback for every unmapped query.

## 6. Obsolescence and ontology versioning

GO evolves through added terms, changed labels/definitions/relationships, merges and obsoletions. Obsolete terms retain IDs and an obsolete marker but lose relationships; they must not remain ordinary retrieval candidates. A reused ID string does not mean its surrounding graph or annotation interpretation stayed fixed. [GO ontology documentation](https://www.geneontology.org/docs/ontology-documentation/).

| Mechanism | Meaning and recommended handling |
|---|---|
| `alt_id` | Alternate identifier of a canonical term, including identifiers retained through merges. Resolve to the primary ID in the pinned release; preserve the supplied ID in provenance. Do not assume every obsolete ID appears as an alternate ID. |
| `is_obsolete: true` | Exclude from new predictions; keep metadata for explaining historical input/results. Do not compute obsolete-term depth as though the term were an active leaf. |
| `replaced_by` | Intended replacement suitable for automatic reassignment under the format semantics. Follow an unambiguous replacement to an active term with a recorded migration; validate cycles, missing targets and multiple replacements instead of choosing the first. |
| `consider` | Suggested alternative requiring judgment; **not an equivalence and not an automatic redirect**. Return suggestions/unresolved status or ask a curator. |
| Unknown/unresolvable ID | Distinguish from obsolete-with-replacement; never silently drop it or fabricate a nearby active ID. |

These tag distinctions follow the [OBO 1.4 specification](https://owlcollab.github.io/oboformat/doc/GO.format.obo-1_4.html), especially `alt_id`, `is_obsolete`, `replaced_by`, and `consider`. Conservative handling of ambiguity/cycles is a design recommendation.

GO publishes **monthly releases**, with development/snapshot products separate from dated reproducible releases. GOA separately states an approximately four-week cycle coordinated with UniProt. [GO downloads](https://www.geneontology.org/page/downloads), [GO release archive](https://release.geneontology.org/2026-01-23/ontology/index.html), [GOA release cycle](https://www.ebi.ac.uk/GOA/).

**Standard practice:** cite and record the ontology release/date, source URL and annotation release, using the ontology specified by the annotation file header. GO asks for the release date/version and preferably a release DOI. GAF's `gaf-version` describes the file format; it is not an ontology version. Preserve the applicable GO-version header and use an immutable dated ontology URL rather than treating `current` as a permanent version. [GO citation guidance](https://www.geneontology.org/page/use-and-license), [annotation downloads and header guidance](https://www.geneontology.org/page/downloads), [GAF 2.2](https://geneontology.org/docs/go-annotation-file-gaf-format-2.2/).

For this API, additionally emit or attach a manifest containing ontology data-version and content hash, file flavor (`go-basic.obo` versus `go.obo`/OWL), crosswalk URLs/dates/hashes, subset membership/hash, parser version, ranking/tokenizer/model configuration, closure relation policy and annotation timestamp. These extra fields are recommended reproducibility measures, not all mandatory GAF columns. Never refresh the ontology underneath a cached index or model without rebuilding and reevaluating derived artifacts. Historical results should retain original IDs and versions alongside any separately recorded migration.

Finally, “asserted `is_a`” must identify **which file's assertions** are meant. A distributed ontology artifact can contain edges materialized by release processing/reasoning; an OBO line alone does not prove a curator directly asserted it. Pin the actual artifact, avoid silently invoking new OWL reasoning, and name the metric accordingly. Depth/height, leaf status, parent counts and IC must be recomputed or versioned with that artifact.
