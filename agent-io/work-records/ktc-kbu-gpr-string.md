## summary
`_add_reactions_from_gene_mapping` now accepts a `reaction_gene_hash` whose
values are **either** a list of gene ids (the historical isozyme shorthand) **or**
a verbatim GPR string. A list behaves byte-for-byte as it did on the base commit
in both the new-reaction and existing-reaction paths. A string is used verbatim
as `reaction.gene_reaction_rule`, so an enzyme complex computed upstream — by the
KBDL model-reconstruction service — survives instead of collapsing into
isozymes. The module exports `GPR_STRING_SUPPORT = 1` as the capability marker
KBDL reads to gate a complex-bearing job.

### Why the string merge parenthesises both sides

`"(" + existing + ") or (" + incoming + ")"` rather than
`existing + " or " + incoming`. Either side may contain a top-level `and`
(`"gA and gB"`), and `and` binds tighter than `or` in cobra's grammar, so the
unparenthesised form would silently re-associate: `"gA and gB or gC"` parses as
`"(gA and gB) or gC"`, which is right by luck in that direction but wrong when
the *incoming* side is the conjunction. Wrapping both sides makes the merge
associativity-independent. Pinned by
`test_existing_plus_incoming_str_parenthesises_both_sides`, which asserts the
full six-row knockout truth table by GPR evaluation rather than by string
compare.

## DEFECT recorded for a separate migration — substring duplicate check

The list-merge duplicate test on the existing-reaction path is:

```python
for gene_id in gene_spec:
    if gene_id not in existing_gpr:    # <-- substring test over rule TEXT
```

`existing_gpr` is a string, so `in` is a **substring** test, not a token test.
An incoming gene id that is a substring of a gene id already in the rule is
silently dropped. Existing rule `"abc"` plus incoming `["ab", "d"]` yields
`"abc or d"` — `"ab"` is lost.

This is wrong. It is **preserved deliberately** and pinned by
`test_incoming_list_gene_that_is_a_substring_is_still_skipped`, because the task
requires the list path to be byte-identical to the base commit and because
fixing it would silently change the GPRs of every existing caller — including
models already written to KBase. It also matches real gene-id shapes badly:
locus tags like `b1234` / `b12345`, or `fig|83333.1.peg.1` / `...peg.10`, are
exactly the substring-prefix case.

The same `in` test will also match a gene id appearing inside an operator-adjacent
position of a complex rule, so the defect is slightly worse once str GPRs are in
circulation — but only for *list* input merged onto a str-authored rule.

**Recommended separate migration:** replace the substring test with a token test
over `cobra.core.gene.GPR.from_string(existing_gpr).genes`, behind a flag or a
version bump, with a backfill audit of models whose GPRs were built by this path.
Out of scope here; this task is explicitly byte-compatibility-constrained.
