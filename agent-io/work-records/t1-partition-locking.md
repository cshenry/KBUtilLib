## summary
Widened the council's `ExecutionLock` (`src/kbutillib/domains/ai/council/execlock.py`) so several queue-worker processes can hold the store-wide lock at once, while a migration still cannot run alongside any of them. `acquire()` gained an optional `partition=(queue_name, worker_index)` argument: `daemon`/`run` with a partition take the store-wide `daemon.lock` SHARED and their own `council-<queue>-<index>.lock` file EXCLUSIVELY, so two workers for the same `(queue, index)` refuse each other but distinct partitions (including two children of the same queue with different indices) run concurrently. `migrate` is unchanged -- always EXCLUSIVE on the store-wide lock -- because that is the only backstop against a schema change racing a running worker; double-claiming a call is already prevented elsewhere by the claim protocol (`BEGIN IMMEDIATE` + per-row `claim_token` + `status == 'pending'` guard in `store/queries.py`'s `claim_update`), so this lock never needed to guard against it. Unpartitioned `run`, an old-style `daemon`, and `evaluate` are untouched and remain mutually EXCLUSIVE with queue workers in both directions. Added a new `controller` kind: one persistent, exclusive, per-store controller lock (its own `controller.lock` file) plus a SHARED hold on the store-wide lock, so queue workers can run beneath it while two controllers for one store still refuse each other. Because the store-wide lock can now have several SHARED holders at once, a single-line-in-one-file holder record no longer suffices for an EXCLUSIVE refusal message (e.g. `migrate` refused while workers hold it); each SHARED holder (worker or controller) now registers itself via its own uniquely-named, self-flocked file, and a refusal enumerates every live one (pruning any whose process has died, detected the same way every other staleness check in this module works -- by trying the flock, never by reading stale content). The store-wide lock file's name and inode (`daemon.lock`) are unchanged, per the binding confront-round amendment, so an old and a new binary always contend for the same file. The module and class docstrings were rewritten to carry the updated safety reasoning (claim-protocol backstop vs. migration backstop) rather than deleting it.

## caveats
- **Design judgement call on the `controller` kind's shape.** The task prompt only requires "add whatever kind is needed to LOCK_KINDS" for a persistent, exclusive, per-store controller; it does not specify the mechanism. I implemented it as: SHARED on the store-wide `daemon.lock` (same as a queue worker, so it correctly excludes/is excluded by unpartitioned legacy kinds) plus its own new singleton file `controller.lock`, EXCLUSIVE, to stop two controllers coexisting (shared-mode-on-shared-mode cannot do that on its own, since two SHARED holders are meant to coexist). This reasoning is recorded in the module docstring and in `_acquire_controller`'s docstring. `CONTROLLER_LOCK_FILENAME` is exported alongside `LOCK_FILENAME` in case a later task (daemon supervision, per the PRD's "Daemon supervision" section) needs to reference it directly.
- **Shared-holder enumeration uses a new auxiliary directory**, `daemon.lock.shared/`, holding one uniquely-named, self-flocked JSON file per live SHARED holder (worker or controller). This is new on-disk state beyond what the task prompt described (a single partition lock file per worker); it was necessary because multiple concurrent SHARED holders cannot safely share one single-line file via the existing truncate+write discipline (a race between holders), and the task explicitly requires "a store-wide refusal enumerates every kernel-held worker lock." Each entry is self-cleaning (pruned by any later enumeration once the kernel has released its flock, exactly like every other staleness check in this module) and is unique per acquisition, so no other process ever opens it by name -- consistent with the class docstring's existing "never delete a lock file that still might be meaningful" rule, which I extended rather than violated.
- **`probe()` is unchanged in its single-dict return contract** (still answers only for the store-wide file's own content) and was deliberately NOT extended to enumerate multiple SHARED holders -- that enumeration lives only in the `LockHeld` message a refused `acquire()` raises, since `probe()` is used today by `daemon.py`'s unpartitioned "already running?" check and changing its contract was out of scope (not one of `daemon.py`/CLI/`evaluate()`'s callers, which I was told not to touch, but `probe()`'s behaviour is still part of the public surface those callers rely on).
- Found and fixed a self-inflicted bug while writing the dead-holder test: an early draft called `release.set()` in a `finally` block after `holder.kill()`. A process SIGKILLed while it holds the `multiprocessing.Event`'s own internal semaphore can leave that semaphore permanently wedged (POSIX semaphores are not robust against a holder's death), which hung the test indefinitely. The final test follows the same pattern as the pre-existing `test_the_kernel_releases_a_killed_holders_lock` -- never touching `release` after a kill, since the process is already confirmed dead and there is nothing left to release it from. No production code was affected; this was purely a test-authoring mistake caught before commit.
- Did not touch `src/kbutillib/domains/ai/council/daemon.py`, `src/kbutillib/domains/ai/council_utils.py`, or `src/kbutillib/domains/ai/council/store/queries.py`, per the task's file-ownership constraint, even though the PRD's "Daemon supervision" section describes a controller/worker launcher that will need to call `acquire("controller")` and `acquire(kind, partition=...)` -- that wiring is explicitly a later task's responsibility.
